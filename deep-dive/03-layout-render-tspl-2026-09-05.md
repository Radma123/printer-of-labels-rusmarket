## Overview

### Что этот код делает

Два файла, одна ответственность на двоих: **превратить данные этикетки в пиксели,
а пиксели — в байты для принтера**.

* `layout.py` — **только числа**. Ни одной строки логики отрисовки. Размеры в миллиметрах,
  координаты логотипов, кегли шрифтов, параметры принтера. Плюс `as_dict()`, который
  отдаёт те же числа фронтенду.
* `render.py` — берёт эти числа и рисует: класс `Canvas` (холст в миллиметрах поверх
  1-битной картинки), шесть функций `draw_*` (по одной на блок этикетки),
  и `build_tspl()`, который упаковывает готовую картинку в команды принтера.

Ключевое свойство всей связки: **картинка, которую видит пользователь в браузере,
и картинка, которая уходит на термоголовку, — один и тот же массив пикселей**.
Не «похожая», не «сверстанная по тем же правилам» — тот же самый.

### Почему выбран такой подход

Задача, которая обычно решается плохо: «сделать WYSIWYG-редактор этикеток».
Наивный путь — сверстать превью на HTML/CSS, а для печати написать второй рендер.
Дальше начинается бесконечная погоня: браузер и принтер по-разному округляют,
по-разному считают межстрочный интервал, по-разному ведут себя со шрифтами.
Пользователь двигает блок на миллиметр — и на печати он оказывается на полтора.

Здесь принято радикальное решение: **превью — это и есть картинка от принтерного
рендера**. Сервер рисует PNG в 203 dpi (`render_for_print`), отдаёт её в base64,
браузер показывает её как `<img>`, повернув средствами CSS. Поворот кратен 90°,
значит не искажает ни одного пикселя. Поверх картинки лежат **прозрачные рамки** —
за них блоки таскают мышью, но они ничего не рисуют.

Цена решения: каждое движение мыши — round-trip на сервер (дебаунс 110 мс,
`app.js:268`). Выигрыш: расхождение превью и печати структурно невозможно.

Второе принципиальное решение: **текст уходит на принтер картинкой**, а не
командами `TEXT`. Встроенные шрифты TSC TE200 не знают кириллицы и не умеют
letter-spacing. Значит, всё равно пришлось бы рисовать растр — так пусть весь
макет будет одним растром, а не смесью «часть рисует Pillow, часть прошивка».
Исключение — старый `tsc_label.py`, который отдавал штрихкод и QR прошивке;
именно поэтому у него не могло быть точного превью.

### Контекст

Такая архитектура («один рендер, превью = продукт») применима везде, где
результат физический и необратимый: этикетки, чеки, гравировка, раскрой, ЧПУ.
Если ошибку нельзя откатить кнопкой Undo, стоимость расхождения превью и результата
резко возрастает — и лишний round-trip перестаёт быть дорогим.

#### Блок 1. Две системы координат (строки 12–41)

```python
LABEL_W_MM = 72.0                         # ширина макета (портрет)
LABEL_H_MM = 100.0                        # высота макета
...
PRINT_W_MM = 100.0
PRINT_H_MM = 72.0
```

Самая важная вещь в файле, и она объясняется в докстринге: **макет портретный
72×100, рулон принтера — 100×72**. Числа те же, просто переставлены.

Почему так вышло: настоящие этикетки CNH — портретные, макет в Claude Design
нарисован портретным, и правки пользователя мысленно происходят в портрете
(«подвинь логотип левее»). А принтер откалиброван на рулон, где 100 мм идёт
поперёк термоголовки, а 72 мм — вдоль подачи бумаги. Перекалибровать принтер под
портрет — значит требовать этого от каждого, кто поставит приложение.

Решение: **весь код живёт в портретной системе, поворот на 90° делается один раз,
в самом конце**, в `render_for_print` (строка 457). Ни одна функция `draw_*`
про поворот не знает. Это тот же принцип, что «работать в одной системе единиц
и конвертировать на границе».

```python
PX_PER_MM = 96 / 25.4                     # CSS px -> mm, как в doc-page.js
DPI = 203
```

**Три разных «пикселя» в одном проекте** — источник половины возможных ошибок:

| Единица | Значение | Где |
|---|---|---|
| CSS px | 96 на дюйм (по определению CSS) | числа, унаследованные из макета: `BARCODE_ROW["height_px"] = 73` |
| Точка принтера | 203 на дюйм (8 точек на мм) | `Canvas.px_per_mm`, `mm_to_dots` |
| Экранный px браузера | зависит от монитора и зума | измеряется в рантайме, `app.js:301` `measurePxPerMm` |

Миллиметр — единственная общая валюта. Отсюда правило проекта: **любое число,
приехавшее из макета в px, немедленно делится на `PX_PER_MM`**. Видно в `render.py:331`:

```python
row_h_mm = BARCODE_ROW["height_px"] / PX_PER_MM * sy
```

`96 / 25.4` не сворачивается в `3.7795...` намеренно — записанная формула
объясняет себя, магическое число нет.

LOGOS = {

Это перенос CSS-приёма **«cover + crop»**: контейнер с `overflow: hidden`,
внутри картинка бóльшего размера, сдвинутая абсолютным позиционированием.
В браузере это три CSS-свойства; в Pillow это ресайз + `crop` + повторный ресайз

Числа с двумя знаками после запятой (`3.49`, `9.51`) — прямой перенос из

Это важно: любой «а давайте округлим до 3.5» рассинхронизирует макет и рендер.

`margin_top: 4.0` есть только у одного логотипа (`eye`) — потому что так было

`dict.get(key, default)` вместо `spec["margin_top"]` именно для того, чтобы
остальным двум не пришлось выписывать нулевое поле.

#### Блок 3. Контракт ручных правок (строки 96–123)

```python
ELEMENTS = ("header", "desc", "made_in", "barcode", "pn", "pcs")
TWEAK_SCALE_MIN = 0.30
TWEAK_SCALE_MAX = 2.50

def default_tweaks() -> dict:
    return {key: {"dx": 0.0, "dy": 0.0, "sx": 1.0, "sy": 1.0} for key in ELEMENTS}
```

Пользователь может **подвинуть** блок мышью (`dx`, `dy` в миллиметрах) и
**изменить размер** по каждой оси отдельно (`sx`, `sy` — множители).
Комментарий (строки 96–108) фиксирует семантику, и она нетривиальна:

* `dx`/`dy` — **не влияют на поток**. Подвинули логотипы — остальное осталось на месте.
  Иначе перетаскивание одного блока дёргало бы всю этикетку, и мышью было бы
  невозможно попасть куда хочешь.
* `sy` — **влияет на поток** (блоки ниже подвинутся сами), `sx` — нет.
  Логично: высота блока определяет, где начинается следующий; ширина — нет.

Это ровно та развилка, которую легко решить неправильно и обнаружить только
на пользователе. Явная запись правила в комментарии — не многословие, а
единственное место, где это правило вообще зафиксировано.

**`{key: ... for key in ELEMENTS}`** — словарное включение (dict comprehension).
Синтаксис `{ключ: значение for ...}`; со скобками `[...]` было бы списковое,
с `{...}` и без двоеточия — множественное (set comprehension).

**Почему функция, а не константа `DEFAULT_TWEAKS = {...}`**: словарь мутабельный.
Константу вызывающий код мог бы случайно изменить, и дефолт «поехал» бы для всех
последующих запросов. Функция каждый раз возвращает свежую копию. Это тот же
класс проблемы, что знаменитый «мутабельный аргумент по умолчанию»:

```python
def f(items=[]):      # ЛОВУШКА: список создаётся один раз при определении функции
    items.append(1)
    return items
f(); f()              # -> [1, 1]

def f(items=None):    # правильно
    items = [] if items is None else items
```

**`as_dict()`** (строки 138–156) — сериализация геометрии для фронтенда.
Фронтенду эти числа нужны не для вёрстки (превью — картинка!), а только для
подписей в панели и границ ползунков. Явная функция вместо `vars(module)`
или `globals()` — потому что явный список полей это контракт API, а не побочный
эффект того, что лежит в модуле.

#### Блок 4. Поиск шрифтов (строки 29–73)

```python
FONT_CANDIDATES = [
    ("/System/Library/Fonts/Supplemental/Arial.ttf",
     "/System/Library/Fonts/Supplemental/Arial Bold.ttf"),
    ...
]
_fonts = None

def _font_files():
    global _fonts
    if _fonts:
        return _fonts
    env = os.environ.get("LABEL_FONT")
    if env and os.path.exists(env):
        _fonts = (env, os.environ.get("LABEL_FONT_BOLD", env))
        return _fonts
    for reg, bold in FONT_CANDIDATES:
        if os.path.exists(reg):
            _fonts = (reg, bold if os.path.exists(bold) else reg)
            return _fonts
    found = sorted(glob.glob("/System/Library/Fonts/Supplemental/*.ttf"))
    if not found:
        raise RuntimeError("не найден ни один TTF-шрифт, задайте LABEL_FONT")
    _fonts = (found[0], found[0])
    return _fonts
```

**Каскад дефолтов** — четыре уровня, от самого явного к самому отчаянному:
переменная окружения → список известных путей → любой TTF в системной папке →
внятная ошибка с подсказкой, что делать.

`global _fonts` — объявление «я присваиваю переменную из модульной области видимости,
а не создаю локальную». Без него `_fonts = ...` создало бы локальную переменную,
а модульная осталась бы `None` — классическая ошибка. **Читать** глобальную можно
без `global`; объявление нужно только для присваивания.

Это ручная **мемоизация**: посчитали один раз, положили в модульную переменную.
Более идиоматичный современный вариант:

```python
from functools import lru_cache

@lru_cache(maxsize=None)          # или @functools.cache в Python 3.9+
def _font_files():
    ...                            # без global, без if _fonts
```

`if _fonts:` вместо `if _fonts is not None:` — здесь эквивалентно (кортеж из двух
непустых строк всегда истинен), но в общем случае опасно: пустой кортеж, `0`,
`""` ложны, и кэш «не сработает». Для кэша правильнее сравнение с `None`.

`bold if os.path.exists(bold) else reg` — деградация: нет жирного начертания,
берём обычное. Этикетка станет бледнее, но напечатается.

#### Блок 5. `Canvas` — холст в миллиметрах (строки 76–109)

```python
class Canvas:
    def __init__(self, scale: int = 1):
        self.scale = scale
        self.px_per_mm = DPI / 25.4 * scale
        self.w = int(round(LABEL_W_MM * self.px_per_mm))
        self.h = int(round(LABEL_H_MM * self.px_per_mm))
        self.img = Image.new("1", (self.w, self.h), 1)      # 1 = белый
        self.dr = ImageDraw.Draw(self.img)

    def px(self, value_mm: float) -> int:
        return int(round(value_mm * self.px_per_mm))
```

Ядро всего рендера — **тонкая обёртка над Pillow, которая говорит в миллиметрах**.
Каждый метод принимает мм, внутри переводит в пиксели через `self.px()`.
Благодаря этому все шесть `draw_*` функций читаются как описание макета,
а не как арифметика с разрешением.

**`Image.new("1", size, 1)`** — режим `"1"` это **1 бит на пиксель**, чёрно-белое
без градаций. Именно то, что печатает термопринтер: точка либо есть, либо нет.
Третий аргумент — цвет заливки; в режиме `"1"` значение `1` = белый, `0` = чёрный.
Контринтуитивно (обычно 0 = чёрный в градациях серого, но там 0 = «нет света»),
поэтому в коде это прокомментировано дважды.

**`scale`** — рендер в увеличенном разрешении. `scale=1` → 203 dpi, ровно как печатает
принтер. `scale=4` (превью, `app.js:275`) → 812 dpi, чтобы на экране не было
«лесенки». Печать **всегда** `scale=1` (`build_tspl`, строка 492) — увеличивать
для принтера нечего, у него физически 203 точки на дюйм.

`int(round(...))` а не `int(...)`: `int()` **отбрасывает дробную часть**
(`int(2.9) == 2`), `round()` округляет к ближайшему (`round(2.9) == 3`).
На 203 dpi одна точка = 0.125 мм; систематическое занижение на каждом
преобразовании накопило бы заметный сдвиг вниз по этикетке.

Одна тонкость `round()` в Python, о которой стоит знать: это **банковское
округление** (round half to even). `round(0.5) == 0`, `round(1.5) == 2`,
`round(2.5) == 2`. Не ошибка — так меньше систематическое смещение на больших
выборках, — но неожиданно, если ждёшь школьного правила.

#### Блок 6. Letter-spacing вручную (строки 98–138)

```python
def tracked(self, x_mm, y_mm, text, size_mm, spacing_mm, bold=True, mono=False,
           anchor="la"):
    if anchor[0] == "m":
        x_mm -= self.tracked_width(text, size_mm, spacing_mm, bold, mono) / 2
        anchor = "l" + anchor[1]
    x = x_mm
    for ch in text:
        self.dr.text((self.px(x), self.px(y_mm)), ch,
                     font=self.font(size_mm, bold, mono), fill=0, anchor=anchor)
        x += self.text_width(ch, size_mm, bold, mono) + spacing_mm
```

**Pillow не умеет letter-spacing.** В CSS это одно свойство; здесь приходится
рисовать **каждый символ отдельно**, вручную двигая курсор на ширину символа
плюс заданный интервал.

`anchor` в Pillow — двухбуквенный код: первая буква горизонталь (`l`eft, `m`iddle,
`r`ight), вторая вертикаль (`a`scender, `m`iddle, `d`escender, `b`aseline).
`"la"` = «координата это левый верхний угол по восходящей линии шрифта».
Посимвольная отрисовка не может использовать `"ma"` (центрирование) — центрируется
строка целиком, а не каждый символ. Отсюда пересчёт в первых трёх строках:
центр строки превращается в её левый край, дальше рисуем как обычно.

`anchor[0] == "m"` и `"l" + anchor[1]` — работа со строкой как с массивом символов.
Компактно, но хрупко: молча сломается, если кто-то передаст однобуквенный anchor.

**Заметная проблема производительности.** `self.font(...)` вызывается **внутри цикла
по символам**, и `text_width` вызывает его ещё раз для того же символа.
А `Canvas.font` (строка 90) на каждый вызов делает `ImageFont.truetype(path, size)` —
это **чтение и парсинг файла шрифта**. Для строки в 25 символов — 50 загрузок
шрифта; для шести строк наименования — 300; плюс столько же в `tracked_width`
при подсчёте ширины. При `scale=4` и дебаунсе 110 мс во время перетаскивания
это ощутимо. Лечится одной строкой:

```python
from functools import lru_cache

@lru_cache(maxsize=64)
def _load_font(path: str, size_px: int):
    return ImageFont.truetype(path, size_px)

# в Canvas.font:
return _load_font(path, max(5, int(round(size_mm * self.px_per_mm))))
```

Ключ кэша — `(путь, размер в пикселях)`; объекты `ImageFont` без состояния между
вызовами `text()`, так что переиспользовать их безопасно.

```python
def fit_size(self, text, size_mm, max_w_mm, bold=False, mono=False,
            letter_spacing_mm=0.0) -> float:
    if not text or max_w_mm <= 0:
        return size_mm
    width = self.tracked_width(text, size_mm, letter_spacing_mm, bold, mono)
    if width <= max_w_mm:
        return size_mm
    return max(1.6, size_mm * max_w_mm / width)
```

**Автоуменьшение кегля.** Ширина текста растёт почти линейно по кеглю, поэтому
нужный размер считается **пропорцией за один шаг**, без итеративного подбора
«уменьши на 0.1 и померяй снова». Приближение неточное (хинтинг шрифта нелинеен),
но погрешность в доли процента, а вызовов в 20 раз меньше.

`max(1.6, ...)` — нижняя граница: лучше обрезать по краю, чем напечатать
нечитаемые 0.4 мм. Докстринг честно говорит, что это **подстраховка**, а не
штатный путь: макет рассчитан на короткие наименования, а из CSV приезжают
машинные переводы вроде «FILTRO DE ACEITE DEL MOTOR DE COMBUSTIÓN».

#### Блок 7. `paste_crop` — логотипы (строки 144–172)

```python
src = Image.open(path).convert("RGBA")
white = Image.new("RGBA", src.size, (255, 255, 255, 255))
src = Image.alpha_composite(white, src).convert("L")
```

**Композиция на белый фон.** У логотипов PNG есть альфа-канал. Простой
`.convert("L")` **выбросил бы альфу**, и прозрачные области стали бы чёрными —
логотип напечатался бы негативом в чёрном квадрате. `alpha_composite` сначала
подкладывает белое, потом уже переводит в градации серого. Это тот самый баг,
который обычно обнаруживают на первой физической этикетке.

```python
disp_w = max(1, int(round(spec["disp"]["w"] * work_px_per_mm)))
...
resized = src.resize((disp_w, disp_h), Image.LANCZOS)
cropped = resized.crop((ox, oy, ox + bw, oy + bh))
target_w = self.px(spec["box"]["w"] * scale_x)
cropped = cropped.resize((max(1, target_w), max(1, target_h)), Image.LANCZOS)
cropped = cropped.point(lambda v: 255 if v > 200 else 0).convert("1")
```

Цепочка из четырёх шагов, и порядок в ней не случаен:

1. **Ресайз до «отображаемого» размера** в промежуточном разрешении
   `work_px_per_mm = 20` px/мм. Это воспроизводит CSS-шаг «картинка показана
   размером disp».
2. **Кроп** окна `off..off+box` — CSS-шаг «контейнер с overflow:hidden».
3. **Ресайз кропа до целевого размера** на холсте, уже с учётом ручного масштаба.
   Здесь `scale_x`/`scale_y` применяются **только на этом шаге** — окно кропа
   от них не зависит. Поэтому можно ужать логотип по ширине, не сдвинув то,
   что попало в кадр. Это прямо оговорено в докстринге (строки 149–153).
4. **Порог** `> 200 → белый, иначе чёрный` — превращение градаций серого в 1 бит.

**`Image.LANCZOS`** — фильтр ресемплинга. Из доступных (`NEAREST`, `BILINEAR`,
`BICUBIC`, `LANCZOS`) он даёт самые резкие края при уменьшении, что критично
перед порогом: размытый край после бинаризации превращается в рваный.

**`.point(lambda v: 255 if v > 200 else 0)`** — поэлементное преобразование
через lookup-таблицу. Pillow вызывает функцию **256 раз** (по одному на возможное
значение байта), строит таблицу и применяет её ко всем пикселям на C-скорости.
То есть лямбда вызывается 256 раз, а не по разу на пиксель — важное отличие
от «медленного питона в цикле».

Порог 200, а не 128 — логотипы содержат светло-серые градиенты, которые при
пороге 128 превратились бы в грязные пятна. 200 отсекает всё, кроме почти чёрного.
Это подбирается глазом на реальной печати, и такое число полезно комментировать
(здесь не прокомментировано — стоило бы).

#### Блок 8. `_squeeze` — сжатие текста по горизонтали (строки 212–244)

Самая хитрая функция файла. Задача: пользователь ужал блок «Наименование»
по ширине (`sx = 0.7`), высоту не трогал (`sy = 1.0`). Логотип и штрихкод так
умеют — у них ширина это просто число. **А глифы шрифта Pillow рисует только
пропорционально**: `ImageFont.truetype(path, 20)` даёт шрифт кегля 20 по обеим осям,
задать «узкий» нельзя.

```python
def _squeeze(cv: Canvas, painter, k: float, anchor_mm: float):
    if abs(k - 1.0) < 1e-3:
        painter(cv)
        return

    tmp = Canvas(cv.scale)
    painter(tmp)
    ink = ImageChops.invert(tmp.img.convert("L"))
    bbox = ink.getbbox()
    if not bbox:
        return

    x0, y0, x1, y1 = bbox
    piece = tmp.img.crop(bbox).convert("L")
    new_w = max(1, int(round((x1 - x0) * k)))
    piece = piece.resize((new_w, y1 - y0), Image.LANCZOS)
    piece = piece.point(lambda v: 255 if v > 160 else 0).convert("1")

    anchor_px = cv.px(anchor_mm)
    new_x = int(round(anchor_px + (x0 - anchor_px) * k))
    mask = ImageChops.invert(piece.convert("L")).convert("1")
    cv.img.paste(0, (new_x, y0), mask)
```

Алгоритм: нарисовать блок на **отдельном холсте** в натуральную величину,
найти границы нарисованного, вырезать, сжать по горизонтали как растр,
положить обратно.

**`painter` — функция как аргумент.** Вызывающий передаёт замыкание,
которое умеет нарисовать блок на **любом** холсте:

```python
def painter(c):                       # c — куда рисовать
    y = top
    for line in shown:
        size = c.fit_size(line, size_mm, CONTENT_W_MM, bold=True, ...)
        c.text(left, y, line, size, bold=True, ...)
        y += line_h + gap

_squeeze(cv, painter, sx / sy, left)
```

Ключевая деталь: `painter` принимает холст **параметром**, а координаты берёт
из замыкания. Поэтому `_squeeze` может вызвать его на `tmp` вместо `cv`,
и всё нарисуется в тех же абсолютных координатах, но на другой картинке.
Это паттерн, который в других языках зовут *strategy* или *callback*,
а в графических API — *deferred drawing*.

Для однострочных блоков используется лямбда прямо в вызове (строки 313, 367):

```python
_squeeze(cv, lambda c: c.text(left, top, text, size_mm, letter_spacing_mm=spacing),
         sx / sy, left)
```

**`k = sx / sy`, а не `sx`** — потому что вертикальный масштаб уже применён
через кегль (`size_mm = DESC["size"] * sy`). Остаётся досжать разницу
между осями. Если `sx == sy`, `k == 1` и функция уходит по быстрому пути,
не создавая временный холст.

**`abs(k - 1.0) < 1e-3`** вместо `k == 1.0` — сравнение float. Прямое сравнение
чисел с плавающей точкой почти всегда ошибка: `0.1 + 0.2 == 0.3` даёт `False`.
Здесь `k` получается делением, так что ровной единицы может не быть даже при
`sx == sy`. Эпсилон `1e-3` выбран по смыслу задачи: разница масштаба в 0.1%
на этикетке невидима.

**`ImageChops.invert(...).getbbox()`** — как найти границы нарисованного.
`getbbox()` возвращает прямоугольник **ненулевых** пикселей. На нашем холсте
фон белый = 1 (ненулевой), чернила чёрные = 0. То есть без инверсии `getbbox()`
вернул бы весь холст. После инверсии чернила становятся ненулевыми, фон нулевым,
и `getbbox()` даёт именно рамку текста. Изящный трюк, но требует комментария —
его в коде нет.

**Вставка по маске:**

```python
mask = ImageChops.invert(piece.convert("L")).convert("1")
cv.img.paste(0, (new_x, y0), mask)
```

`Image.paste(color, position, mask)` в трёхаргументной форме заливает цветом
`0` (чёрный) **только там, где маска ненулевая**. Маска = инвертированный кусок,
то есть единицы стоят там, где были чернила. Итог: на холст переносятся
**только чёрные пиксели**, белый фон куска не затирает то, что уже нарисовано.
Это ровно то, что нужно, если пользователь надвинул блоки друг на друга —
объяснено в докстринге (строки 222–223).

`new_x = anchor_px + (x0 - anchor_px) * k` — **сжатие относительно точки**.
Не «сожми и положи на прежнее место», а «приблизь левый край к якорю
в той же пропорции». Для блока с выравниванием по левому краю якорь — левый край
(тогда `x0 == anchor_px` и сдвига нет), для центрированных (`pn`, `barcode`) — центр.

**Цена приёма**: при `k != 1` создаётся полный временный холст на весь размер
этикетки. При `scale=4` это 1134×1575 пикселей на каждый сжимаемый блок,
до шести за рендер. Работает, но это первое место, куда стоит смотреть,
если превью начнёт тормозить.

#### Блок 9. Поток блоков — `draw_label` (строки 411–432)

```python
def draw_label(cv: Canvas, data: dict):
    lines = (data.get("lines") or [])[:DESC["max_lines"]]
    boxes = []

    box, y = draw_header(cv, PAD_MM, _tweak(data, "header"))
    boxes.append(box)
    y += GAP_MM
    box, y = draw_desc(cv, lines, y, _tweak(data, "desc"))
    boxes.append(box)
    y += GAP_MM
    ...
    boxes.append(draw_pcs(cv, data.get("pcs", "1"), y + GAP_MM, _tweak(data, "pcs")))
    return boxes
```

**Ручная реализация вертикального flex-потока.** Каждая `draw_*` принимает
`top_mm` (где начинается) и возвращает `(рамка, следующий_top_mm)`.
Между блоками добавляется `GAP_MM` — это `gap: 3mm` из CSS макета.

Приём `box, y = draw_...(cv, ..., y)` — переприсваивание `y` результатом.
Читается как конвейер: каждый шаг сдвигает курсор вниз. Компактно и прозрачно;
альтернатива (класс `LayoutContext` с полем `.y`) была бы многословнее
без выигрыша.

`(data.get("lines") or [])[:DESC["max_lines"]]` — три защиты в одном выражении:
ключа нет → `None`; `None or []` → пустой список; срез до 6 элементов.
Срез в Python **не падает** при выходе за границы: `[1,2][:6]` даёт `[1,2]`.

Возврат `boxes` — рамок блоков в миллиметрах — то, за счёт чего работает
перетаскивание на фронтенде. Их считает **тот же проход отрисовки**, что и
картинку (`render_with_boxes`, строка 441), поэтому ручки физически не могут
оказаться не там, где нарисован блок. Это то же решение, что «превью = продукт»,
только уровнем ниже.

#### Блок 10. `draw_pcs` — `margin-top: auto` руками (строки 377–408)

```python
flush_y = LABEL_H_MM - PAD_MM - height
hard_cap = LABEL_H_MM - height - 0.3
top = min(max(min_top_mm, flush_y), hard_cap) + dy
```

Три ограничения в двух строках:

* `flush_y` — где строка была бы, если прижать её к нижнему полю (`margin-top: auto` в CSS).
* `max(min_top_mm, flush_y)` — но не выше, чем позволяет предыдущий блок.
  Если контента много, строка съезжает вниз от идеальной позиции, а не наезжает на номер детали.
* `min(..., hard_cap)` — и в любом случае не ниже, чем 0.3 мм от края этикетки.

Зачем третье ограничение, объяснено в докстринге (строки 383–388): при полных
шести строках наименования расчёт в миллиметрах даёт запас меньше миллиметра,
а **реальные метрики Arial в Pillow чуть выше эталонного Helvetica в браузере**.
Без жёсткого потолка последняя строка обрезалась бы краем этикетки. С ним —
слегка ужимается последний отступ.

Идиома `min(max(value, lo), hi)` — это **clamp**, зажать значение в диапазон.
Она же в `_tweak` (строка 190). В Python нет встроенного `clamp`, поэтому пишут так;
в других языках это одна функция (`std::clamp`, `Math.clamp`).

#### Блок 11. `_bitmap_cmd` — картинка в байты TSPL (строки 464–474)

```python
def _bitmap_cmd(img: Image.Image, x_dots: int = 0, y_dots: int = 0) -> bytes:
    """Картинка -> команда BITMAP. В TSPL, как и в Pillow '1', бит 0 = чёрный."""
    img = img.convert("1")
    w, h = img.size
    width_bytes = (w + 7) // 8
    if w % 8:
        padded = Image.new("1", (width_bytes * 8, h), 1)
        padded.paste(img, (0, 0))
        img = padded
    return (f"BITMAP {x_dots},{y_dots},{width_bytes},{h},0,".encode("ascii")
            + img.tobytes() + b"\r\n")
```

Здесь всё интересное — в четырёх строках `if w % 8`.

**`(w + 7) // 8`** — деление с округлением **вверх**. `//` это целочисленное
деление (отбрасывает дробь). Прибавить `делитель - 1` перед делением — стандартная
идиома «сколько байт нужно на w бит»: 800 бит → 100 байт, 801 бит → 101 байт.

**Почему нужно дополнение.** `Image.tobytes()` в режиме `"1"` пакует по 8 пикселей
в байт и **выравнивает каждую строку по границе байта**, заполняя хвост нулями.
А `0` в этом формате — **чёрный**. То есть при ширине, не кратной 8, Pillow
сам пририсовал бы чёрную полосу справа на всю высоту этикетки.

Решение: создать картинку шириной, кратной 8, **залитую белым** (`1`), вставить
исходную в левый верхний угол. Хвост остаётся белым, полосы нет.

При 100 мм × 203 dpi ширина = 799 или 800 точек в зависимости от округления —
то есть код регулярно попадает в «не кратно 8». Это не теоретическая, а рабочая ветка.

**`.encode("ascii")`** — явная кодировка для заголовка команды. Могло быть
`.encode()` (utf-8 по умолчанию), но `ascii` **упадёт**, если в строку случайно
попадёт не-ASCII символ. Для протокола, который принимает только ASCII-команды,
это правильная строгость: лучше исключение в питоне, чем принтер, зажёвывающий
рулон от непонятных байт.

Байтовая конкатенация `bytes + bytes + b"\r\n"` — команда TSPL это **смесь текста
и бинарных данных**: ASCII-заголовок, потом сырые биты картинки, потом `\r\n`.
Именно поэтому всё задание собирается как `bytes`, а не `str`.

#### Блок 12. `build_tspl` — задание целиком (строки 477–502)

```python
img = render_for_print(data, scale=1)

job = b""
job += f"SIZE {PRINT_W_MM:g} mm,{PRINT_H_MM:g} mm\r\n".encode()
job += f"GAP {PRINT_GAP_MM:g} mm,0 mm\r\n".encode()
job += f"SPEED {SPEED}\r\n".encode()
job += f"DENSITY {DENSITY}\r\n".encode()
job += b"DIRECTION 1,0\r\nREFERENCE 0,0\r\nSET TEAR ON\r\nCLS\r\n"
job += _bitmap_cmd(img)
job += f"PRINT {max(1, int(copies))},1\r\n".encode()
return job
```

**TSPL** (TSC Printer Language) — построчный текстовый протокол, как ZPL у Zebra
или EPL. Команды разделены `\r\n` (именно CRLF, не `\n`). Что делает каждая:

| Команда | Смысл |
|---|---|
| `SIZE 100 mm,72 mm` | физический размер этикетки |
| `GAP 3 mm,0 mm` | зазор между этикетками и его смещение; принтер по нему позиционируется датчиком |
| `SPEED 4` | дюймов в секунду |
| `DENSITY 8` | нагрев головки, 0–15; больше — темнее, но выше износ и риск залипания |
| `DIRECTION 1,0` | направление печати и зеркалирование |
| `REFERENCE 0,0` | начало координат |
| `SET TEAR ON` | подать этикетку до линии отрыва после печати |
| `CLS` | очистить буфер изображения |
| `BITMAP ...` | собственно растр |
| `PRINT 1,1` | напечатать: копий, наборов |

**`{value:g}`** — формат `g` в f-строке: «общий» формат для чисел, который
убирает незначащие нули. `100.0` → `"100"`, `3.0` → `"3"`, но `2.5` → `"2.5"`.
Без него получилось бы `SIZE 100.0 mm` — прошивка это, скорее всего, съест,
но `g` даёт ровно тот вид, что в документации TSPL.

**`job = b""` и `job += ...`** — конкатенация байтов в цикле присваиваний.
На девяти операциях это неважно; при тысячах пришлось бы собирать в список
и делать `b"".join(parts)` (каждое `+=` создаёт новый объект — квадратичная
сложность). Здесь читаемость важнее.

**`max(1, int(copies))`** — защита от `PRINT 0,1` и от отрицательных значений.
Проверка на верхнюю границу делается выше, в `server.py:260` (`min(999, ...)`).

**Честно задокументированная неизвестность** (строки 487–490):

> Направление поворота (по часовой/против) не проверялось на реальном принтере.
> Если первая физическая этикетка ляжет текстом вверх ногами — включите
> `data["rotate180"]` (чекбокс в интерфейсе).

Это хорошая инженерная практика в проекте без тестов: вместо угадывания —
явная запись «здесь не проверено» плюс **готовый способ обойти**, не трогая код.
Пользователь ставит галочку вместо того, чтобы звать разработчика.

## Concepts Explained

### Design Patterns Used

| Паттерн | Где | Зачем |
|---|---|---|
| Single source of truth | `layout.py` — все координаты в одном файле | Числа не расползаются по трём реализациям (Python, CSS, TSPL) |
| Separation of data and behavior | `layout.py` (числа) vs `render.py` (логика) | Правка макета не требует чтения кода отрисовки |
| Coordinate abstraction | `Canvas` в миллиметрах | Функции рисования не знают про DPI и scale |
| Callback / deferred drawing | `painter` в `_squeeze` | Один блок рисуется на разные холсты без дублирования кода |
| Layout pass returns geometry | `draw_*` → `(box, next_y)` | Рамки для перетаскивания считает тот же проход, что и картинку |
| Convert at the boundary | поворот на 90° только в `render_for_print` | Вся система живёт в одной системе координат |
| Graceful degradation | нет жирного шрифта → обычный; не кодируется штрихкод → без полос | Этикетка печатается всегда, ошибка сообщается отдельно |
| Documented unknown | комментарий про направление поворота + `rotate180` | Непроверенное поведение обходится настройкой, а не правкой кода |

### Key Technical Concepts

#### Концепт 1: Растровая печать на термопринтере

**Что**: термоголовка — линейка нагревательных точек поперёк ленты (у TE200 —
203 на дюйм). Бумага протягивается, головка построчно жжёт точки. Никаких
градаций: точка либо активирована, либо нет. Отсюда 1-битная картинка.

**Почему здесь**: встроенные шрифты принтера не знают кириллицы и не умеют
letter-spacing. Раз всё равно рисовать растр — пусть весь макет будет одним растром.

**Когда применять**: любой вывод, где источник — макет, а приёмник — устройство
с фиксированной сеткой точек (чеки, этикетки, гравировка, вышивка).

**Trade-offs**:
* Плюсы: полный контроль над видом, любые шрифты и языки, превью совпадает с печатью пиксель в пиксель.
* Минусы: задание намного больше по объёму (сотни килобайт против сотен байт для текстовых команд); нельзя изменить содержимое на стороне принтера; вся типографика — ваша ответственность, включая хинтинг и сглаживание, которого при 1 бите нет.

**Альтернативы**: команды `TEXT`/`BARCODE` прошивки (компактно, быстро, но
шрифты и раскладка вне вашего контроля — см. `tsc_label.py`); PostScript/PDF
через обычный драйвер (не подходит: TSPL-принтеры принимают raw-поток).

**Что нужно знать**:
* DPI и перевод мм ↔ точки (`203 dpi ≈ 8 точек/мм`).
* Битовая упаковка и выравнивание строк по границе байта.
* Что такое raw-печать в CUPS (`lp -o raw`) — байты идут в устройство без обработки драйвером.

#### Концепт 2: Перенос CSS-макета в императивный рендер

**Что**: CSS даёт декларативную модель (flex, `gap`, `margin: auto`, `overflow: hidden`).
Pillow даёт `draw.text(x, y)`. Между ними — ручная реализация тех правил потока,
которые реально используются в макете.

**Почему здесь**: макет нарисован в Claude Design как HTML/CSS, а печатать надо
растром. Полноценный CSS-движок (WeasyPrint, headless Chrome) добавил бы
десятки мегабайт зависимостей ради шести блоков в колонку.

**Когда применять**: когда набор используемых CSS-возможностей мал и заранее
известен. Здесь это ровно четыре правила: вертикальный flex с `gap`,
`justify-content: space-between` в шапке, `margin-top: auto` у последней строки,
`overflow: hidden` для логотипов. Каждое реализуется десятком строк.

**Trade-offs**:
* Плюсы: нет тяжёлых зависимостей, полный контроль, детерминированный результат.
* Минусы: расхождения метрик шрифтов (браузерный Helvetica vs Pillow Arial — прямо об этом `draw_pcs`, строки 385–388); каждое новое CSS-свойство в макете надо реализовывать руками; макет и код надо держать синхронно вручную.

**Альтернативы**:
* **WeasyPrint** — HTML/CSS → PDF/PNG в чистом Python; честный CSS, но большой стек зависимостей и своя типографика.
* **Playwright/headless Chrome** → скриншот; пиксель в пиксель как в браузере, но 300+ МБ и запуск браузера на каждую этикетку.
* **SVG + `cairosvg`** — промежуточный вариант: макет как SVG, рендер библиотекой.

**Что нужно знать**: box model, flex-контейнер и `gap`, `margin: auto`
как механизм выравнивания, разница между `px` в CSS (96/дюйм) и физическим пикселем.

#### Концепт 3: Функция как аргумент (callback / higher-order function)

**Что**: `_squeeze(cv, painter, k, anchor)` принимает **функцию** `painter`
и решает, когда и куда её вызвать. В Python функции — объекты первого класса:
их можно передавать, возвращать, хранить в списках.

**Почему здесь**: `_squeeze` нужно нарисовать блок дважды в разных условиях
(на временный холст, потом перенести результат), но она не знает и не должна
знать, что именно рисуется — текст, две колонки или что-то ещё.

**Когда применять**: когда «что делать» и «в каких условиях делать» — разные
ответственности. Классика: `sorted(key=...)`, декораторы, обработчики событий
(`app.js:359` — `addEventListener("pointerdown", startDrag)` это то же самое),
контекстные менеджеры.

**Trade-offs**:
* Плюсы: `_squeeze` пишется один раз и работает для любого блока; логика рисования и логика сжатия не переплетаются.
* Минусы: сложнее трассировать (в стеке появляется лишний уровень); замыкания захватывают переменные **по ссылке**, что даёт классическую ловушку:

  ```python
  fns = [lambda: i for i in range(3)]
  [f() for f in fns]            # -> [2, 2, 2], а не [0, 1, 2]

  fns = [lambda i=i: i for i in range(3)]    # захват по значению
  [f() for f in fns]            # -> [0, 1, 2]
  ```

  Здесь это не стреляет — `painter` создаётся и вызывается в пределах одного
  вызова функции, — но при рефакторинге в цикл выстрелит обязательно.

**Альтернативы**: класс с методом `draw()` (многословнее); передавать
список примитивов вместо функции (гибче для сериализации, но сложнее).

**Что нужно знать**: замыкания и области видимости; `lambda` как выражение
(в неё нельзя положить `for` или `if` как оператор — только выражение);
`functools.partial` как способ зафиксировать часть аргументов.

#### Концепт 4: Числа с плавающей точкой в геометрии

**Что**: `float` в Python — двоичное представление IEEE 754. Десятичные дроби
вроде `0.1` в нём непредставимы точно, поэтому `0.1 + 0.2 != 0.3`.

**Почему здесь**: весь макет в миллиметрах, всё считается делениями и умножениями
(`sx / sy`, `CONTENT_W_MM * width_frac`), и результат в конце превращается в
целые пиксели. Три места, где это проявляется:

1. `abs(k - 1.0) < 1e-3` (строка 224) — сравнение с эпсилоном вместо `==`.
2. `int(round(...))` везде вместо `int(...)` — округление, а не усечение.
3. `Math.abs(box.w - gw * baseSx) < 0.01` в `app.js:468` — то же самое на фронте.

**Когда применять эпсилон-сравнение**: **всегда** при сравнении вычисленных
`float`. Величина эпсилона — из предметной области, а не «маленькое число вообще»:
здесь 0.1% масштаба и 0.01 мм, потому что меньшее физически невидимо.

**Trade-offs**: эпсилон-сравнения нельзя использовать как отношение эквивалентности
(`a≈b` и `b≈c` не даёт `a≈c`), поэтому по ним нельзя сортировать или строить ключи словаря.

**Альтернативы**: `decimal.Decimal` (точная десятичная арифметика, медленнее
на порядок, оправдана для денег); `fractions.Fraction` (точные рациональные);
работа в целых единицах — «всё в микрометрах» — если предметная область позволяет.

**Что нужно знать**: IEEE 754 и почему `0.1` непредставим; `math.isclose(a, b)`
из стандартной библиотеки (умеет и относительный, и абсолютный допуск);
банковское округление в `round()`.
