## Overview

### Что этот код делает

Три файла, объединённые ролью «всё, что вокруг веб-приложения»:

* **`tsc_label.py`** — автономный CLI и **первая версия проекта**. Один файл,
  который делает всё: читает CSV, рисует этикетку, шлёт в CUPS. Приложение
  `label_app/` выросло из него, но CLI остался работоспособным и полезным
  для диагностики (`--check`).
* **`scripts/launch.sh`** — «запустить приложение одной командой»: обновиться
  из git, создать venv, поставить зависимости, поднять сервер, открыть браузер.
  Плюс `stop`/`restart`/`status`/`update`.
* **`scripts/build_app.sh`** — собирает `Этикетки CNH.app` для запуска из Dock.

### Почему выбран такой подход

**Почему CLI сохранён.** Формально `label_app/` покрывает всё, что умеет
`tsc_label.py`, и делает лучше (индекс вместо линейного скана, точное превью).
Но у CLI осталась одна незаменимая функция: **`--check`**. Когда веб-приложение
не запускается, надо понять, что именно сломалось — Pillow, шрифты, CUPS или CSV.
Диагностика, не зависящая от сервера, — правильный инструмент для этого.
Плюс это живая документация исходного решения: сравнение `find_row` (линейный
скан) и `Catalog.get` (индекс) в одном репозитории стоит любого объяснения.

**Почему bash, а не Python-лаунчер.** Задача лаунчера — создать окружение,
в котором Python сможет запуститься. Писать это на Python — курица и яйцо:
скрипт должен работать **до** того, как venv существует и Pillow установлен.
Bash есть на любом Mac и умеет ровно то, что нужно: процессы, файлы, сеть.

**Почему AppleScript-обёртка, а не py2app/PyInstaller.** Приложению нужно
только одно: быть иконкой в Dock, которая запускает `launch.sh`. Настоящая
сборка (py2app) вморозила бы Python и Pillow внутрь `.app` — и тогда обновление
кода через git перестало бы работать, каждый релиз требовал бы пересборки
и переустановки. Тонкая обёртка на 8 строк AppleScript сохраняет главное
свойство: **код обновляется git-ом, `.app` пересобирать не нужно**.

### Контекст

Связка «git pull + venv + nohup + pidfile» — самый дешёвый способ раздать
внутренний инструмент нескольким пользователям без CI, реестра пакетов и
установщика. Работает, пока пользователей единицы и все на одной ОС.
Дальше начинаются пакеты (`pipx`, `brew`), контейнеры или настоящий установщик.

**Импорт, который не роняет программу.** Обычно отсутствие зависимости —
это `ImportError` на первой строке и непонятный стектрейс. Здесь факт
отсутствия запоминается в двух переменных, и программа продолжает работать.

Зачем: главная ценность `--check` в том, что он работает **именно когда
что-то сломано**. Если бы отсутствие Pillow роняло импорт, диагностика
стала бы недоступна ровно в тот момент, когда она нужнее всего.

Проверяется дважды: в `check()` (строка 325) — как пункт отчёта,
и в `main()` (строка 371) — перед реальной работой, с готовой командой установки:

```python
if not PIL_OK:
    raise SystemExit("Не установлен Pillow. Выполните:\n"
                     "    python3 -m pip install --user pillow")
```

**`raise SystemExit(str)`** — выход с кодом 1 и сообщением в stderr.
Отличие от `sys.exit()`: никакого, `sys.exit` буквально бросает `SystemExit`.
Отличие от `raise Exception`: `SystemExit` наследуется от `BaseException`,
а не от `Exception`, поэтому не перехватывается обычным `except Exception`
и не печатает трассировку — только текст. Для CLI это правильное поведение:
пользователю нужна инструкция, а не стек.

`from PIL import ...` в `try` — обратите внимание, что имена `Image`,
`ImageDraw`, `ImageFont` при неудаче просто не определятся. Любая функция,
которая их использует, упадёт с `NameError` — поэтому проверка `PIL_OK`
обязана стоять до вызова этих функций. Здесь она стоит.

#### Блок 2. Линейный скан CSV (строки 94–122)

```python
def find_row(csv_path: str, pn: str):
    """Ищет строку по каталожному номеру. Читает файл потоком, поэтому
    размер CSV значения не имеет."""
    needle = (pn.strip().upper() + ";").encode("utf-8")
    with open(csv_path, "rb") as fh:
        header_raw = fh.readline()
        for raw in fh:
            if raw.upper().startswith(needle):
                hdr = next(csv.reader([header_raw.decode("utf-8-sig", "replace")],
                                      delimiter=";", quotechar='"'))
                row = next(csv.reader([raw.decode("utf-8", "replace")],
                                      delimiter=";", quotechar='"'))
                return dict(zip(hdr, row))
    return None
```

Это **предшественник** `catalog.Catalog.get`. Полезно смотреть на них рядом.

**Ключевая оптимизация**: сравнение на уровне **сырых байтов**, до разбора CSV.
`raw.upper().startswith(needle)` — одна операция на строку. Полный разбор через
`csv.reader` делается **только для найденной строки**. Разбирать все 3.5 млн
строк было бы в разы медленнее.

`needle` включает `";"` — разделитель. Без него `"C5NN"` совпал бы с `"C5NNF892A"`.
Дешёвый способ добиться точного совпадения первой колонки без её выделения.

**`"utf-8-sig"`** для заголовка — кодек, который **съедает BOM**, если он есть,
и работает как обычный utf-8, если его нет. Для данных используется просто
`"utf-8"`, потому что BOM бывает только в начале файла. Именно этот BOM
и стал источником проверки `index_is_valid` в `catalog.py:25` — там смещения
считаются в байтах, и три лишних байта в начале ломают весь индекс.

**Асимметрия, которую стоит заметить.** `find_row` открывает файл, читает
до совпадения и закрывает. При промахе — полный проход, ~40 секунд на 1.14 ГБ.
`find_similar` (строка 110) делает **второй такой же проход**, чтобы подсказать
похожие номера. То есть неудачный поиск в CLI — это полторы минуты.
Именно эта цифра и породила `catalog.py`.

`.upper()` на каждой строке — тоже заметная стоимость: создаётся новый объект
`bytes` на 3.5 млн итераций. Альтернатива — сравнивать оба варианта регистра
(`raw.startswith(needle) or raw.startswith(needle_lower)`), но выигрыш
не стоил бы усложнения, раз подход всё равно заменён.

#### Блок 3. Перенос текста по словам (строки 155–172)

```python
def wrap(draw, text, fnt, max_w, max_lines):
    words, lines, cur = text.split(), [], ""
    for w in words:
        probe = (cur + " " + w).strip()
        if draw.textlength(probe, font=fnt) <= max_w or not cur:
            cur = probe
        else:
            lines.append(cur)
            cur = w
            if len(lines) == max_lines:
                break
    if cur and len(lines) < max_lines:
        lines.append(cur)
    if lines and draw.textlength(lines[-1], font=fnt) > max_w:
        while lines[-1] and draw.textlength(lines[-1] + "…", font=fnt) > max_w:
            lines[-1] = lines[-1][:-1]
        lines[-1] += "…"
    return lines
```

Классический **greedy word wrap**: добавляем слово за словом, пока помещается;
не помещается — начинаем новую строку.

**`or not cur`** — важная деталь. Если слово само по себе шире строки
(длинный артикул, немецкое сложносоставное слово), условие
`textlength(probe) <= max_w` ложно **всегда**, и без `or not cur` цикл
клал бы пустые строки бесконечно. Условие означает «в текущей строке пусто —
клади слово в любом случае, даже если не влезает». Переполнение потом
подрежется многоточием.

**Обрезка с многоточием** — цикл, отрезающий по символу, пока `текст + "…"`
не влезет. `lines[-1][:-1]` — срез «всё кроме последнего символа».
Проверяется ширина **вместе с многоточием**, потому что «…» тоже занимает место —
частая ошибка: обрезали по ширине, добавили многоточие, снова вылезло.

`while lines[-1] and ...` — защита от бесконечного цикла: если даже одно
многоточие не влезает, строка станет пустой и цикл прервётся по первому условию.

Обратите внимание, чего здесь **нет**: переноса по слогам, обработки неразрывных
пробелов, работы с двунаправленным текстом. Для наименований запчастей
из трёх слов это оправданно.

В `label_app/render.py` этой функции нет вообще — там другой подход
(`fit_size`, строка 111): вместо переноса уменьшается кегль. Потому что
макет фиксирует **шесть строк на шести языках**, и лишняя строка ломала бы вёрстку.

#### Блок 5. Диагностика (строки 324–342)

```python
def check(csv_path: str) -> None:
    print("Pillow:       да" if PIL_OK else
          f"Pillow:       НЕТ ({PIL_ERR})\n"
          "              установите:  python3 -m pip install --user pillow")
    if PIL_OK:
        try:
            reg, bold = resolve_fonts()
            print("Шрифты:      ", reg)
            print("             ", bold)
        except SystemExit as exc:
            print("Шрифты:       НЕТ —", exc)
    qs = queues()
    print("Принтеры:    ", ", ".join(qs) if qs else
          "не найдено ни одной очереди CUPS\n"
          "              → отсоедините принтер от Windows-ВМ и добавьте его в macOS")
    print("Каталог CSV: ", csv_path if os.path.exists(csv_path) else f"НЕ НАЙДЕН ({csv_path})")
```

Образцовая диагностическая команда. Каждая проверка выводит **не только статус,
но и что делать**:

* нет Pillow → готовая команда установки;
* нет очередей CUPS → «отсоедините принтер от Windows-ВМ» — это не общая
  рекомендация, а **зафиксированная реальная причина** из истории проекта.
  Пользователь держал принтер проброшенным в виртуалку, и macOS его не видел.

Это ценнее любой документации: диагностика, которая помнит, обо что уже спотыкались.

**`except SystemExit`** — `resolve_fonts` при неудаче бросает `SystemExit`
(строка 84), что убило бы весь `--check` на середине. Здесь оно перехватывается,
и остальные проверки продолжаются. Правильный приоритет: диагностика должна
показать **все** проблемы за один запуск, а не первую.

Побочно это показывает, почему `SystemExit` в библиотечной функции —
сомнительное решение: вызывающий обязан знать про такое поведение и
специально его ловить. Чище было бы бросать `RuntimeError`, а решение
о завершении принимать в `main`.

`", ".join(qs) if qs else "..."` — тернарный оператор внутри аргумента `print`.
Плотно, но читаемо для двух вариантов.

#### Блок 6. `argparse` (строки 346–358)

```python
p = argparse.ArgumentParser(description="Печать этикеток 100x72 мм на TSC TE200")
p.add_argument("--check", action="store_true", help="проверить окружение и выйти")
p.add_argument("--pn", help="каталожный номер детали из CSV")
p.add_argument("--csv", default=CSV_DEFAULT, help="путь к каталогу CSV")
p.add_argument("--preview", metavar="PNG", help="сохранить превью картинкой")
p.add_argument("--copies", type=int, default=1)
a = p.parse_args()
```

* **`action="store_true"`** — флаг без значения: `--check` даёт `a.check == True`,
  отсутствие — `False`. Без этого argparse ждал бы `--check ЧТО-ТО`.
* **`type=int`** — argparse сам преобразует и сам выдаст внятную ошибку
  при `--copies abc`, не доводя до `ValueError` в вашем коде.
* **`metavar="PNG"`** — как аргумент называется в тексте помощи:
  `--preview PNG` вместо `--preview PREVIEW`.
* **`default=CSV_DEFAULT`** — значение, если флаг не задан.
* `--help` генерируется автоматически из `description` и `help`.

```python
if a.preview:
    build_preview(data, a.preview)
if a.out:
    ...
if a.printer:
    send_cups(job, a.printer)
if a.usb:
    send_usb(job)
if not any([a.preview, a.out, a.printer, a.usb]):
    sys.stdout.buffer.write(job)
```

**Композиция действий, а не выбор одного.** Флаги не взаимоисключающие:
можно одновременно сохранить превью, записать задание в файл и напечатать.
Каждый обрабатывается своим независимым `if`.

**`if not any([...])`** — если не указано ни одного выхода, задание пишется
в stdout. Это делает утилиту **компонуемой** в духе Unix:

```bash
python3 tsc_label.py --pn C5NNF892A > job.tspl
python3 tsc_label.py --pn C5NNF892A | lp -d TSC_TE200 -o raw -
```

**`sys.stdout.buffer.write(job)`** — не `print(job)`. `job` это `bytes`;
`print` вызвал бы `str()` и напечатал `b'SIZE 100 mm...'` с литералом `b`
и экранированными байтами — мусор. `sys.stdout.buffer` — это бинарный поток
под текстовым, туда байты пишутся как есть.

```python
if a.demo or not a.pn:
    data = DEMO
    if not a.demo:
        print("Номер детали не задан — печатаю демо-этикетку "
              "(--pn НОМЕР для реальной детали)", file=sys.stderr)
```

**`file=sys.stderr`** для предупреждения. Принципиально: stdout занят под
задание TSPL, и предупреждение в нём испортило бы бинарный поток при
использовании через пайп. Правило Unix: **данные в stdout, диагностика в stderr**.
Тот же принцип в `launch.sh:26` (`log()` пишет в stderr, потому что stdout
занят под возврат значений из функций).

#### Блок 7. Настройка и корень проекта (строки 14–26)

```bash
set -u

ROOT="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
cd "$ROOT" || exit 1
```

**`set -u`** — обращение к неустановленной переменной становится ошибкой.
Без него опечатка в имени переменной даёт пустую строку, и `rm -rf "$TYPO/"`
превращается в `rm -rf /`. Один из трёх флагов «строгого режима» bash:

| Флаг | Что делает |
|---|---|
| `set -e` | выход при любой неуспешной команде |
| `set -u` | ошибка при неустановленной переменной |
| `set -o pipefail` | код возврата пайпа = код первой упавшей команды, а не последней |

Здесь **намеренно нет `-e`**: скрипт должен продолжать работу, когда git
недоступен, pip не смог поставить пакет, сети нет. Каждая такая ситуация
обрабатывается явно (`|| return 0`, `if ! ...`), а `-e` обрывал бы скрипт
на первой же. Это осознанное решение, а не забывчивость — видно по тому,
как последовательно проверяются коды возврата.

**`"$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"`** — канонический способ
найти корень проекта относительно скрипта:

* `${BASH_SOURCE[0]}` — путь к **текущему скрипту**. Отличается от `$0`:
  при `source script.sh` в `$0` будет имя оболочки, а `BASH_SOURCE` всегда
  указывает на файл.
* `dirname` — папка скрипта (`scripts/`), `/..` — на уровень выше.
* `cd ... && pwd` — превращает относительный путь в абсолютный и разрешает
  симлинки. Просто `dirname .../..` дал бы строку с `..` внутри.

Результат: скрипт работает из любой рабочей директории.
`bash ~/Documents/.../scripts/launch.sh` и `bash scripts/launch.sh` эквивалентны.

**Кавычки везде.** `"$ROOT"`, `"$(...)"` — без них путь с пробелом
(а он тут есть: «Этикетки CNH.app») развалится на два аргумента.
В bash кавычки — не стилистика, а корректность.

```bash
log() { echo "[$(date '+%Y-%m-%d %H:%M:%S')] $*" | tee -a "$LOG" >&2; }
```

**`$*`** — все аргументы одной строкой (`$@` — отдельными словами; для `echo`
разницы почти нет, для передачи дальше — принципиальная).

**`tee -a "$LOG" >&2`** — записать в файл **и** вывести. `tee` дублирует
stdin в файл и в stdout, `-a` — дописывать. `>&2` перенаправляет stdout `tee`
в stderr. Зачем — объяснено комментарием строкой выше: «stdout занят под
возврат значений из функций». В bash функции возвращают строки именно
через stdout (`py="$(ensure_python)"`), поэтому всё остальное должно идти в stderr.

#### Блок 8. Ожидание процесса с таймаутом (строки 29–40)

```bash
wait_pid() {                      # wait_pid <pid> <секунд>
    local pid="$1" limit="$2" i=0
    while kill -0 "$pid" 2>/dev/null; do
        if [ "$i" -ge $((limit * 2)) ]; then
            kill -9 "$pid" 2>/dev/null; return 1
        fi
        sleep 0.5; i=$((i + 1))
    done
    wait "$pid" 2>/dev/null
}
```

**`kill -0 PID`** — не убивает процесс, а **проверяет его существование**
и права на отправку сигнала. Сигнал 0 не доставляется; ненулевой код возврата
означает «процесса нет». Стандартная идиома «жив ли процесс».

**`local`** — переменные, локальные для функции. Без `local` все переменные
в bash **глобальные**, и `i` в этой функции затёр бы `i` в вызывающей.
Обязательная гигиена.

**`$((...))`** — арифметическое расширение. Внутри работает C-подобный синтаксис
(`i + 1`, `limit * 2`), и `$` перед именами переменных не нужен.
Без него `i + 1` было бы строкой из трёх слов.

`limit * 2`, потому что шаг цикла — полсекунды.

`kill -9` после таймаута — `SIGKILL`, который нельзя перехватить или проигнорировать.
Применяется как последнее средство. Обратите внимание на порядок в `stop()`
(строки 138–145): сначала `kill` (`SIGTERM`, процесс может корректно завершиться),
секунда паузы, и только потом `kill -9`. Правильная эскалация.

**`wait "$pid"`** — забирает код возврата завершившегося дочернего процесса.
Без этого процесс остаётся зомби в таблице процессов.

```bash
port_busy() { nc -z 127.0.0.1 "$PORT" >/dev/null 2>&1; }
```

**`nc -z`** — «просканировать порт, ничего не отправляя». Проверяет, слушает ли
кто-то. Используется дважды: в `start()` (не запускать второй экземпляр)
и в `status()` (различить «наш сервер» и «порт занят кем-то чужим»).

Функция возвращает код возврата `nc` — в bash код последней команды и есть
результат функции. Поэтому `if port_busy; then` работает без явного `return`.

`>/dev/null 2>&1` — заглушить и stdout, и stderr. `2>&1` означает «направить
файловый дескриптор 2 (stderr) туда же, куда сейчас указывает 1 (stdout)».
Порядок важен: `2>&1 >/dev/null` сделал бы **не то же самое** (stderr ушёл бы
на исходный stdout, а stdout — в никуда).

#### Блок 9. Обновление из git (строки 49–73)

```bash
update() {
    [ -d "$ROOT/.git" ] || { log "git-репозитория нет — обновление пропущено"; return 0; }
    git -C "$ROOT" rev-parse --abbrev-ref --symbolic-full-name '@{u}' >/dev/null 2>&1 || {
        log "удалённый репозиторий не настроен — обновление пропущено"; return 0; }

    git -C "$ROOT" fetch --quiet >>"$LOG" 2>&1 &
    if ! wait_pid $! 20; then
        log "нет связи с git (таймаут 20 с) — работаем на текущей версии"
        return 0
    fi
    ...
    if git -C "$ROOT" merge --ff-only '@{u}' >>"$LOG" 2>&1; then
```

**`команда || { действие; return 0; }`** — идиома «выйти, если условие не выполнено».
Фигурные скобки группируют команды в текущей оболочке (в отличие от `(...)`,
который создаёт подоболочку — и `return` из неё не вышел бы из функции).
Пробелы внутри `{ }` и точка с запятой перед `}` обязательны.

**`git -C "$ROOT"`** — выполнить git так, как будто мы в этой директории.
Надёжнее, чем `cd`, потому что не меняет состояние скрипта.

**`'@{u}'`** — сокращение для upstream-ветки (то, что отслеживает текущая ветка).
`rev-parse` с ним проверяет, настроен ли вообще remote. Кавычки нужны:
`{` и `}` для bash — брейс-экспансия.

**`git fetch &` + `wait_pid $! 20`** — таймаут для сетевой операции.
`&` запускает в фоне, `$!` — PID последнего фонового процесса.
Без таймаута `git fetch` при недоступной сети может висеть минутами,
и приложение просто не запустится.

Проще было бы `timeout 20 git fetch`, но GNU `timeout` **не входит в macOS**
по умолчанию (только через `brew install coreutils`). Ручная реализация —
цена переносимости.

**`merge --ff-only`** — обновиться, только если это **fast-forward**:
локальная ветка просто отстаёт, и её можно перемотать вперёд. Если есть
локальные правки или ветки разошлись, merge откажется, и скрипт запустит
текущую версию с предупреждением. Это важное решение: автообновление
**никогда не трогает работу пользователя**. Автоматический `merge` или
`rebase` мог бы создать конфликт, который кладовщик не разрешит.

Более радикальный вариант — `git reset --hard @{u}` — гарантирует обновление,
но молча уничтожает локальные изменения. Здесь выбрана безопасность.

#### Блок 10. Окружение Python и кэш зависимостей (строки 76–109)

```bash
local stamp="$ROOT/.deps-stamp" sum
sum="$(shasum "$ROOT/requirements.txt" | awk '{print $1}')"
if [ "$(cat "$stamp" 2>/dev/null)" != "$sum" ]; then
    log "ставлю зависимости (Pillow)"
    "$py" -m pip install --quiet --upgrade pip >>"$LOG" 2>&1
    if "$py" -m pip install --quiet -r "$ROOT/requirements.txt" >>"$LOG" 2>&1; then
        echo "$sum" >"$stamp"
    else
        log "! pip не смог поставить зависимости (нет сети?)"
    fi
fi
```

**Кэш по хешу файла зависимостей.** `pip install` даже при установленных пакетах
занимает пару секунд и требует сети. Здесь хеш `requirements.txt` сравнивается
с сохранённым в `.deps-stamp`; совпал — установка пропускается целиком.

`shasum file | awk '{print $1}'` — `shasum` выводит `хеш  имя_файла`,
`awk '{print $1}'` берёт первое поле.

**`cat "$stamp" 2>/dev/null`** — если файла нет, `cat` напечатает ошибку в stderr
(заглушена) и вернёт пустую строку, которая не совпадёт с хешем.
Отсутствие файла и устаревший хеш обрабатываются одной веткой.

**Штамп записывается только при успехе** — внутри `if pip install; then`.
Если установка провалилась, штамп не обновится, и следующий запуск попробует снова.
Тонкий, но важный момент: записать штамп до проверки успеха означало бы
навсегда пропускать установку после одной неудачи.

```bash
"$py" -c 'import PIL' >/dev/null 2>&1 && { echo "$py"; return 0; }

# Запасной путь: системный python, если в нём уже есть Pillow.
if [ -n "$base" ] && "$base" -c 'import PIL' >/dev/null 2>&1; then
    log "использую системный python3 (в .venv Pillow недоступен)"
    echo "$base"; return 0
fi
```

**Проверка результата, а не процесса.** Не «прошла ли установка», а
«импортируется ли `PIL`». Это единственная проверка, которая реально имеет
значение — pip мог отработать с нулевым кодом, но поставить пакет не туда.

**Запасной путь на системный Python** — деградация вместо отказа. Если venv
сломан, но Pillow есть в системном питоне, приложение всё равно запустится.

**`echo "$py"` как возврат значения.** В bash функции возвращают только
числовой код (0–255). Строку возвращают через stdout, вызывающий забирает
подстановкой: `py="$(ensure_python)"`. Именно поэтому все сообщения
идут в stderr — иначе они попали бы в «возвращаемое значение».

#### Блок 11. Запуск и pidfile (строки 112–136)

```bash
nohup "$py" "$ROOT/label_app/server.py" >>"$LOG" 2>&1 &
echo $! >"$PIDFILE"

local i=0
while [ "$i" -lt 50 ]; do          # ждём порт до 25 секунд
    port_busy && { log "готово: $URL"; return 0; }
    server_pid >/dev/null || break
    sleep 0.5; i=$((i + 1))
done

rm -f "$PIDFILE"
log "! сервер не поднялся, последние строки лога:"
tail -n 15 "$LOG" >&2
```

**`nohup ... &`** — запустить в фоне и отвязать от терминала.
`nohup` игнорирует `SIGHUP`, который приходит при закрытии терминала.
Без него сервер умирал бы вместе с окном терминала — а запускается он
из AppleScript-обёртки, где «терминал» существует доли секунды.

**`echo $! >"$PIDFILE"`** — pidfile, классический механизм управления
демоном без systemd/launchd. `server_pid()` (строки 42–46) читает его
и проверяет, что процесс жив:

```bash
server_pid() {
    [ -f "$PIDFILE" ] || return 1
    local pid; pid="$(cat "$PIDFILE" 2>/dev/null)"
    [ -n "$pid" ] && kill -0 "$pid" 2>/dev/null && echo "$pid"
}
```

Три проверки: файл существует, непустой, процесс жив. Известное ограничение
pidfile — **переиспользование PID**: после перезагрузки тот же номер может
достаться чужому процессу, и `kill -0` скажет «жив». Для локального инструмента
это приемлемо; launchd или systemd решают проблему на уровне ОС.

**Ожидание с двумя условиями выхода**: порт открылся (успех) или процесс
умер (`server_pid || break` — не ждём 25 секунд впустую).

**`tail -n 15 "$LOG"` при неудаче** — сразу показать причину, не заставляя
пользователя искать лог. Мелочь, которая экономит один раунд переписки
с каждым пользователем.

```bash
case "${1:-start}" in
    start)   start ;;
    stop)    stop ;;
    restart) stop; start ;;
    status)  status ;;
    update)  update ;;
    *) echo "использование: $0 [start|stop|restart|status|update]" >&2; exit 2 ;;
esac
```

**`${1:-start}`** — раскрытие с дефолтом: первый аргумент или `start`,
если его нет. Форма `${VAR:-default}` подставляет значение при пустом
или неустановленном `VAR`; `${VAR-default}` — только при неустановленном.
(Есть и `${VAR:=default}`, который заодно присваивает, и `${VAR:?msg}`,
который завершает скрипт с сообщением.)

`case ... esac` — переключатель. `;;` завершает ветку, `*)` — «всё остальное».
`exit 2` для неверного использования — конвенция Unix (1 — ошибка выполнения,
2 — ошибка в аргументах).

### Файл 3: `scripts/build_app.sh`

**Purpose**: `.app`-обёртка для запуска из Dock.

```bash
set -eu

ROOT="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
APP_NAME="Этикетки CNH"
BUILD="$ROOT/$APP_NAME.app"
SRC="$(mktemp -t label_launcher).applescript"

cat > "$SRC" <<EOF
on run
	set launcher to "$ROOT/scripts/launch.sh"
	try
		do shell script "/bin/bash " & quoted form of launcher & " start"
	on error errMsg
		display dialog "Не удалось запустить «Этикетки CNH»:" & return & return & errMsg ¬
			buttons {"OK"} default button 1 with icon caution with title "Этикетки CNH"
	end try
end run
EOF

rm -rf "$BUILD"
osacompile -o "$BUILD" "$SRC"
```

**`set -eu`** — здесь `-e` **есть**, в отличие от `launch.sh`. Логично:
сборка либо проходит целиком, либо должна упасть. Продолжать после неудачного
`osacompile` бессмысленно.

**Heredoc `<<EOF`** — многострочный текст в файл. Без кавычек вокруг `EOF`
переменные **раскрываются**: `$ROOT` подставится реальным путём.
С `<<'EOF'` (в кавычках) текст ушёл бы как есть — что здесь было бы неверно,
путь нужен настоящий.

**`osacompile`** — компилятор AppleScript, делает `.app`-бандл из текста.
Штатная утилита macOS, ничего ставить не нужно.

**`quoted form of launcher`** в AppleScript — экранирование пути для shell.
Путь содержит пробел («Documents/printer-of-labels-rusmarket» — нет, но
`$HOME` пользователя вполне может), и без экранирования `do shell script`
разобрал бы его на несколько аргументов. Это тот же принцип, что кавычки
вокруг `"$ROOT"` в bash.

**`¬`** — символ продолжения строки в AppleScript (аналог `\` в bash).

**`display dialog` при ошибке** — важная деталь UX. Приложение запускается
двойным кликом из Dock: **stderr никто не увидит**. Без диалога пользователь
получил бы «ничего не произошло» и никакой информации. Диалог с текстом ошибки —
единственный канал связи в этом сценарии.

**Мелкая недоработка**: `SRC="$(mktemp -t label_launcher).applescript"` —
`mktemp` создаёт файл (скажем, `/var/folders/.../label_launcher.XXXX`),
а `SRC` это его имя **плюс расширение**. То есть реально используется другой
файл, а созданный `mktemp`-ом остаётся сиротой. `rm -f "$SRC"` (строка 33)
удаляет только `.applescript`. Утечка одного пустого файла на сборку
во временной папке — безобидно, но приём неверный. Корректно:

```bash
TMPDIR_APP="$(mktemp -d)"
SRC="$TMPDIR_APP/label_launcher.applescript"
trap 'rm -rf "$TMPDIR_APP"' EXIT
```

`mktemp -d` создаёт **директорию**, внутри можно называть файлы как угодно,
а `trap ... EXIT` гарантирует уборку даже при ошибке или прерывании —
чего текущий `rm -f` в конце не делает (при `set -e` и падении `osacompile`
файл останется).

## Concepts Explained

### Design Patterns Used

| Паттерн | Где | Зачем |
|---|---|---|
| Soft dependency | `PIL_OK`/`PIL_ERR` в `tsc_label.py` | Диагностика работает именно тогда, когда что-то сломано |
| Diagnostic command | `--check` | Один запуск показывает все проблемы окружения с готовыми решениями |
| Composable CLI | независимые `if` по флагам + вывод в stdout | Утилита встраивается в пайпы |
| Cache by content hash | `.deps-stamp` = хеш `requirements.txt` | Пропуск установки без сети и без задержки |
| Verify outcome, not process | `python -c 'import PIL'` | Проверяется то, что важно, а не код возврата установщика |
| Graceful degradation | venv → системный python; git недоступен → текущая версия | Приложение запускается почти всегда |
| Safe auto-update | `merge --ff-only` | Автообновление никогда не создаёт конфликт |
| Pidfile + port probe | `server.pid` + `nc -z` | Управление демоном без systemd/launchd |
| Timeout on network op | `git fetch &` + `wait_pid $! 20` | Отсутствие сети не блокирует запуск |
| Thin launcher | `.app` вызывает `launch.sh` | Код обновляется git-ом, `.app` не пересобирается |
| Error visible to user | `display dialog` в AppleScript | При запуске из Dock stderr никто не увидит |

### Key Technical Concepts

#### Концепт 1: Строгий режим bash и почему здесь только `-u`

**Что**: `set -e` (выход при ошибке), `set -u` (ошибка на неустановленной переменной),
`set -o pipefail` (код пайпа = код первой упавшей команды).

**Почему здесь**: `launch.sh` — `set -u` без `-e`, `build_app.sh` — `set -eu`.
Разница отражает разные требования. Лаунчер обязан работать в деградированных
условиях: нет сети, нет git, pip не смог. Каждая такая ветка обработана явно;
`-e` обрывал бы скрипт вместо обработки. Сборщик, наоборот, должен упасть
на первой проблеме.

**Когда применять**: `set -euo pipefail` — разумный дефолт для скриптов,
где любая ошибка фатальна (CI, деплой, сборка). Отключать `-e` осознанно,
когда ошибки — часть нормального сценария, и тогда **обязательно** проверять
коды возврата вручную.

**Trade-offs**:
* Плюсы `-e`: не нужно проверять каждую команду; ошибки не проходят молча.
* Минусы `-e`: неочевидное поведение в пайпах, `if`, `&&`; команда, чей ненулевой код нормален (`grep` без совпадений), обрушит скрипт. Отсюда идиомы `команда || true`.

**Что нужно знать**: коды возврата; что `$?` — код последней команды;
`&&` и `||` как управление потоком; почему `set -e` не срабатывает внутри `if`.

---

#### Концепт 2: Управление фоновым процессом без init-системы

**Что**: `nohup ... &` + pidfile + проверка порта — минимальный «демон-менеджер».

**Почему здесь**: приложение запускает пользователь двойным кликом.
launchd-агент требовал бы plist в `~/Library/LaunchAgents`, его установки
и выгрузки — лишний шаг при первой настройке, лишняя сущность при удалении.

**Когда применять**: локальные инструменты, запускаемые пользователем.
Для сервиса, который должен подниматься при загрузке и переживать падения, —
берите launchd (macOS) или systemd (Linux): они дают перезапуск при сбое,
управление логами, зависимости и корректную остановку.

**Trade-offs**:
* Плюсы: ноль конфигурации, работает где угодно, легко читается.
* Минусы: pidfile может «протухнуть» (PID переиспользован); нет автоперезапуска; при `kill -9` самого лаунчера pidfile останется; логи растут без ротации (`logs/app.log` тут никто не подрезает).

**Альтернативы**: `launchd` + `launchctl`; `systemd --user`; `supervisord`;
`tmux`/`screen` для интерактивной отладки.

**Что нужно знать**: сигналы (`SIGTERM` vs `SIGKILL`); процессы-сироты
и зомби; `SIGHUP` при закрытии терминала; что делает `nohup`.

---

#### Концепт 3: Автообновление на git с безопасным отказом

**Что**: `fetch` с таймаутом + `merge --ff-only`. Обновляемся, если можно
безопасно; иначе работаем на том, что есть.

**Почему здесь**: закрытый репозиторий вместо системы установки пакетов.
Разработчик пушит, пользователь запускает приложение и получает новую версию —
без установщика, без реестра, без ручных действий.

**Когда применять**: внутренний инструмент, доверенные пользователи,
несколько машин, нет CI. Как только пользователей десятки или нужны
подписанные релизы — берите нормальную дистрибуцию.

**Trade-offs**:
* Плюсы: обновление бесплатно, откат = `git checkout`, история версий уже есть (`status` показывает `git log -1`).
* Минусы: у пользователя должен быть доступ к репозиторию (ключи, токены); нет проверки, что новая версия рабочая — сломанный коммит уедет всем при следующем запуске; нет отката на предыдущую рабочую версию автоматически.

**Альтернативы**: `pipx install git+...`; сборка `.pkg`; Homebrew tap;
контейнер. Все дают версионирование и откат, все требуют этапа сборки.

**Что нужно знать**: fast-forward vs merge-commit; `@{u}` и upstream-ветки;
почему `reset --hard` в автообновлении опасен.

#### Концепт 4: Возврат значений из функций bash

**Что**: функция bash возвращает только числовой код (0–255) через `return`.
Строку возвращают печатью в stdout, вызывающий забирает через `$(...)`.

**Почему здесь**: `ensure_python` должна вернуть путь к интерпретатору
и при этом логировать ход работы. Отсюда правило файла: **stdout — только
возвращаемое значение, всё остальное в stderr** (`log()`, строка 26).

**Когда применять**: любая bash-функция, возвращающая данные.
Смешение вывода — самая частая ошибка в shell-скриптах: функция «работает»,
пока в неё не добавят `echo` для отладки, и тогда возвращаемое значение
внезапно содержит лишнюю строку.

**Trade-offs**:
* Плюсы: работает везде, композируется с пайпами.
* Минусы: жёсткая дисциплина по потокам; `$(...)` **срезает завершающие переводы строк**; подстановка запускает подоболочку, то есть изменения переменных внутри не видны снаружи.

**Альтернативы**: писать в глобальную переменную (`RESULT=...`) — быстрее,
но неявно; `printf -v var` — присваивание без подоболочки;
для чего-то сложного — не bash.

**Что нужно знать**: файловые дескрипторы 0/1/2; `>&2` и порядок
перенаправлений; что подстановка команд создаёт подоболочку.
