## Overview

### Что этот код делает

`catalog.py` — единственная точка доступа к каталогу запчастей: CSV на 1.14 ГБ,
~3.5 млн строк, разделитель `;`, каталожный номер в первой колонке. Модуль умеет
три вещи:

1. **построить индекс** — файл `<csv>.pnidx` со строками `НОМЕР\tсмещение_в_байтах`,
   отсортированный побайтово;
2. **найти деталь точно** (`Catalog.get`) — двоичный поиск по индексу через `mmap`,
   потом один `seek` в CSV и разбор ровно одной строки;
3. **подсказать номера по префиксу** (`Catalog.suggest`) — для автодополнения в поле ввода.

### Почему выбран такой подход

Исходный `tsc_label.py` читал CSV потоком до первого совпадения. Это честные
~40 секунд на 1.14 ГБ — для CLI, где печатают одну этикетку в час, терпимо;
для веб-интерфейса с автодополнением по каждому нажатию клавиши — нет.

Рассмотренные альтернативы и почему их не взяли:

| Вариант | Почему не он |
|---|---|
| SQLite / DuckDB | Нужно импортировать 3.5 млн строк в отдельную БД — это второй файл на ~1 ГБ рядом с CSV, который нужно синхронизировать. Индекс `.pnidx` — 66 МБ, в 17 раз меньше. |
| Загрузить всё в `dict` в памяти | 3.5 млн ключей в Python-словаре — это ~1–1.5 ГБ RSS, плюс минуты на прогрев при каждом старте сервера. |
| `grep` / `ripgrep` подпроцессом | Всё тот же линейный скан, просто быстрее константа. Автодополнение по префиксу всё равно требует полного прохода. |
| Индекс + `bisect` в памяти | Пришлось бы держать в памяти список из 3.5 млн строк. `mmap` отдаёт ту же случайную адресацию, но платит за это страницами ОС, а не кучей Python. |

Выбранная схема даёт: поиск за единицы миллисекунд, ~0 байт постоянной памяти
процесса (страницы `mmap` — это page cache ОС, она их сама выгрузит под давлением),
и один вспомогательный файл, который можно просто удалить.

### Контекст: когда так делают

Приём «внешний отсортированный индекс + двоичный поиск по mmap» уместен, когда:

* данные **больше памяти**, но **read-only** и меняются редко (каталог, дамп логов,
  словарь, geo-база, `.tsv` выгрузка из чужой системы);
* нужен **точный поиск по одному ключу** и/или **диапазон по префиксу**;
* тащить полноценную БД не хочется — по деплою, по правам, по размеру.

Не подходит, если нужны произвольные запросы по нескольким полям, запись,
транзакции или сортировка по разным колонкам — это уже про SQLite.

#### Блок 1. Валидация индекса (строки 25–49)

```python
def index_is_valid(csv_path: str) -> bool:
    try:
        with open(index_path(csv_path), "rb") as idx:
            pn, _, off = idx.readline().partition(b"\t")
        if not pn or not off.strip().isdigit():
            return False
        with open(csv_path, "rb") as fh:
            fh.seek(int(off))
            first = fh.readline().split(b";", 1)[0].strip().strip(b'"').upper()
        return first == pn.upper()
    except OSError:
        return False
```

Идея: взять **первую** запись индекса и проверить, что смещение действительно
указывает на начало строки с этим же номером. Стоит один `seek` — поэтому вызывается
при каждом запросе (`server.py:172`), а не только при старте.

Что именно эта проверка ловит: **BOM**. UTF-8 файлы из Windows-инструментов часто
начинаются с трёх байт `EF BB BF`. Если индекс собрали, не учтя их, все смещения
уезжают на 3 байта — поиск **не падает**, а тихо возвращает соседний мусор.
Это худший класс багов: молчаливо неверный результат. Дешёвая проверка на входе
превращает его в честное «индекс не готов».

**Языковые детали:**

* `bytes.partition(b"\t")` возвращает **кортеж из трёх элементов** — `(до, разделитель, после)` —
  и всегда три, даже если разделителя нет (тогда `(вся_строка, b"", b"")`). Это отличие
  от `split(b"\t", 1)`, который вернёт список длиной 1 или 2, и распаковка `a, b = ...`
  упадёт. `partition` — способ разобрать «ключ-значение» без проверки на наличие разделителя:

  ```python
  key, sep, value = line.partition(b"\t")
  if not sep:            # разделителя не было
      ...
  ```

  Подчёркивание `_` во `pn, _, off = ...` — не синтаксис языка, а соглашение
  «эта переменная мне не нужна». Линтеры про неё не ругаются.

* `strip()` без аргументов у `bytes` срезает пробельные байты (включая `\r\n` —
  важно для CSV из Windows). `strip(b'"')` — срезает конкретные байты с обоих концов,
  снимая кавычки CSV-квотирования.

* `open(..., "rb")` — бинарный режим. Здесь принципиально: смещения в индексе — **байтовые**,
  а `seek` у текстового файла работает с непрозрачными «позициями кодека», а не с байтами.
  Смешивать нельзя.

* `except OSError` вместо голого `except:` — ловим ровно класс ошибок ввода-вывода
  (`FileNotFoundError`, `PermissionError`, `IsADirectoryError` — все наследники `OSError`).
  Опечатка в коде внутри `try` при этом честно упадёт, а не притворится «индекс невалиден».

**Другое применение того же приёма:** любой производный артефакт (кэш, сборка,
предрасчитанная выборка) полезно уметь дёшево провалидировать «на один элемент»,
а не только по mtime. Классика — `Makefile`-подобная проверка свежести (`index_is_fresh`,
строки 45–49) плюс sanity-check содержимого.

#### Блок 2. Сборка индекса (строки 52–73)

```python
with open(csv_path, "rb") as fh, open(tmp, "wb") as out:
    offset = len(fh.readline())                   # пропускаем заголовок
    next_tick = 0
    for raw in fh:
        pn = raw.split(b";", 1)[0].strip().strip(b'"').upper()
        if pn:
            out.write(pn + b"\t" + str(offset).encode() + b"\n")
        offset += len(raw)
        if progress and offset > next_tick:
            progress(offset, total)
            next_tick = offset + 50 * 1024 * 1024
```

**`for raw in fh` по бинарному файлу** — итерация по строкам с внутренней буферизацией.
Память постоянна независимо от размера файла: питон читает блоками, отдаёт строки.
Это ключ к «однопроходной обработке файла любого размера».

**Смещение считается вручную**, а не через `fh.tell()`. Почему: `tell()` на
буферизованном файле внутри цикла `for line in fh` в Python **запрещён** для текстовых
файлов и стоит сброса буфера для бинарных. Аккумулировать `offset += len(raw)` —
и точнее, и на порядок быстрее. `len(raw)` включает `\n` (и `\r`, если файл из Windows),
поэтому арифметика сходится точно.

**`raw.split(b";", 1)[0]`** — `maxsplit=1` принципиален: без него питон разрежет
всю строку по всем 20 колонкам и создаст 20 объектов `bytes` на каждую из 3.5 млн строк.
С `maxsplit=1` создаются два. На таком объёме это разница в разы по времени.

**Прогресс через колбэк**: `progress` — обычная функция, которую передаёт вызывающий.
Здесь это `lambda done, total: _index_state.update(...)` из `server.py:70`. Дросселирование
на 50 МБ (`next_tick`) — чтобы не дёргать колбэк 3.5 млн раз.

```python
subprocess.run(["sort", "-t", "\t", "-k1,1", tmp, "-o", idx],
               env=dict(os.environ, LC_ALL="C"), check=True)
```

**Внешняя сортировка чужими руками.** Отсортировать 3.5 млн строк в питоне —
это `list` на ~500 МБ. Системный `sort(1)` реализует *external merge sort*: режет вход
на куски, сортирует каждый в памяти, сливает через временные файлы. Работает при любом
размере входа и на C-скорости.

**`LC_ALL="C"` — самая важная строка в файле.** Локаль определяет порядок сравнения
строк. В `en_US.UTF-8` `sort` сравнивает по правилам коллации Unicode: игнорирует
регистр и пунктуацию, `A-1` и `A1` встают рядом. В `C` — сравнение побайтовое.
Двоичный поиск ниже (`_lower_bound`) сравнивает `bytes` оператором `<`, то есть
**побайтово**. Если сортировка и поиск используют разный порядок — поиск даёт неверный
ответ на части ключей, причём тихо. Отсюда правило: *порядок сортировки и порядок
поиска должны быть буквально одной функцией.*

**`dict(os.environ, LC_ALL="C")`** — идиома «копия словаря с добавленным ключом».
Конструктор `dict` принимает мэппинг + именованные аргументы, которые его перекрывают.
Начиная с Python 3.9 то же самое пишется как `os.environ | {"LC_ALL": "C"}`.
Важно, что это **копия**: `os.environ` процесса не меняется, локаль форсируется
только для этого подпроцесса.

**`check=True`** — если `sort` вернул ненулевой код, `subprocess.run` бросит
`CalledProcessError`. Без него ошибка бы прошла молча и `os.remove(tmp)` снёс бы
исходные данные, оставив битый индекс.

**Запись во временный файл + переименование.** Здесь `sort` пишет в `idx` из `tmp`,
и `tmp` удаляется. Приём тот же, что в `translate.py:45-49` (`os.replace`): наружу
никогда не виден полуготовый артефакт.

#### Блок 3. `mmap` и двоичный поиск (строки 87–121)

```python
def open_index(self):
    if self._mm is not None:
        return
    self._idx_file = open(index_path(self.csv_path), "rb")
    self._mm = mmap.mmap(self._idx_file.fileno(), 0, access=mmap.ACCESS_READ)
```

**Что такое `mmap`.** Системный вызов, который отображает файл в адресное
пространство процесса. После него объект `self._mm` ведёт себя как гигантский
`bytes`: `self._mm[100:200]`, `self._mm.find(b"\n", pos)`, `len(self._mm)`.
Но данные **не читаются заранее** — ОС подгружает страницы по 4 КБ по мере обращения
и держит их в page cache. Для двоичного поиска это идеально: 66 МБ индекса,
~26 сравнений на запрос, значит реально трогается ~26 страниц ≈ 100 КБ.

Аргументы: `fileno()` — низкоуровневый файловый дескриптор (число), `0` — «весь файл»,
`access=ACCESS_READ` — только чтение (попытка записи бросит исключение, и ОС не
будет резервировать под это swap).

Важная деталь жизненного цикла: `mmap` **держит открытым файловый дескриптор**.
Поэтому есть `close()` (строки 93–97), и `server.py:76-79` вызывает его перед
пересборкой индекса — иначе после перезаписи файла отображение указывало бы
на старые данные.

```python
def _line_at(self, pos: int):
    start = self._mm.rfind(b"\n", 0, pos) + 1
    end = self._mm.find(b"\n", start)
    if end < 0:
        end = len(self._mm)
    return start, self._mm[start:end]
```

**Ключевая проблема двоичного поиска по текстовому файлу**: адресуемся мы байтами,
а сравнивать нужно строки. `mid = (lo+hi)//2` почти наверняка попадает в середину
строки. `_line_at` откатывается к ближайшему `\n` слева — `rfind(b"\n", 0, pos) + 1`.
Если `\n` слева нет, `rfind` вернёт `-1`, и `+1` даёт `0` — начало файла. Это не
случайность, а известная идиома: `-1 + 1 == 0` делает «не нашли» и «начало файла»
одним случаем без `if`.

```python
def _lower_bound(self, key: bytes) -> int:
    lo, hi = 0, len(self._mm)
    while lo < hi:
        mid = (lo + hi) // 2
        start, line = self._line_at(mid)
        if start < lo:                     # строка началась левее окна
            start = lo
            end = self._mm.find(b"\n", start)
            line = self._mm[start:end if end > 0 else len(self._mm)]
        if line.split(b"\t", 1)[0] < key:
            lo = start + len(line) + 1
        else:
            hi = start
    return lo
```

Это **`lower_bound`** в терминах C++ STL: смещение первой строки, чей ключ `>= key`.
Не «найти или вернуть None», а «граница» — из неё получаются и точный поиск,
и поиск по префиксу, и диапазонные запросы. `bisect.bisect_left` в стандартной
библиотеке — та же семантика, но требует индексируемой последовательности элементов;
здесь элементы переменной длины, поэтому границы двигаем сами.

Инвариант: **`lo` всегда стоит на начале строки** (или 0). `hi` — тоже начало строки
(или конец файла). Отсюда ветка `if start < lo`: откат от `mid` к началу строки мог
уехать левее уже отброшенного окна. Тогда берём строку прямо от `lo` — он по инварианту
на границе строки, так что это корректная строка, просто следующая.

Почему цикл завершается: в ветке «меньше» `lo` строго растёт (`start + len(line) + 1 > lo`);
в ветке «больше или равно» `hi` становится `start`, а `start >= lo`, и `start <= mid < hi`,
значит `hi` строго убывает либо `hi` становится равным `lo` и цикл выходит.

Сложность: `O(log(размер_файла))` обращений, каждое — `rfind`/`find` в пределах строки.
Для 66 МБ это ~26 итераций. Отсюда «единицы миллисекунд» из докстринга.

**Другое применение:** ровно так устроен поиск в отсортированном логе по timestamp
(«покажи всё после 14:32» без загрузки гигабайтного лога), в дампах `robots.txt`-подобных
списков, в offline-словарях. Тот же скелет — только вместо `\t` свой разделитель.

#### Блок 4. Генератор `_iter_from` (строки 123–136)

```python
def _iter_from(self, key: bytes, limit: int):
    self.open_index()
    pos = self._lower_bound(key)
    while pos < len(self._mm) and limit > 0:
        end = self._mm.find(b"\n", pos)
        if end < 0:
            end = len(self._mm)
        line = self._mm[pos:end]
        pos = end + 1
        if not line:
            continue
        pn, _, off = line.partition(b"\t")
        yield pn.decode("utf-8", "replace"), int(off)
        limit -= 1
```

**`yield` делает функцию генератором.** Тело не выполняется при вызове —
`self._iter_from(key, 1)` возвращает объект-генератор; код начинает идти только
на первой итерации `for`. На каждом `yield` выполнение **замораживается**
и возобновляется с той же точки при следующем шаге.

Почему это здесь выгодно: `get()` (строка 151) забирает **одну** запись и выходит —
дальше индекс не читается вообще. `suggest()` забирает до `limit*4` и может
прерваться раньше по `break` (строка 164). Если бы функция возвращала список,
обе стороны платили бы за материализацию.

Один общий генератор обслуживает два разных сценария потому, что оба —
«идти по отсортированному индексу вправо от границы»; отличается только условие
остановки. Это прямое следствие того, что `_lower_bound` возвращает **границу**,
а не результат.

**`decode("utf-8", "replace")`** — второй аргумент это политика обработки ошибок.
`"replace"` подставляет `U+FFFD` (`�`) вместо битого байта вместо того, чтобы бросить
`UnicodeDecodeError`. Для чужого CSV на 3.5 млн строк, где в паре строк может быть
мусор из legacy-системы, «показать номер с одним кракозябром» лучше, чем «уронить сервер».
Другие политики: `"strict"` (по умолчанию, бросает), `"ignore"` (выбрасывает байт),
`"surrogateescape"` (сохраняет байт в приватной области — так можно декодировать,
поработать и закодировать обратно **байт в байт**).

#### Блок 5. От номера к строке CSV (строки 139–168)

```python
def _row_at(self, offset: int) -> dict:
    with open(self.csv_path, "rb") as fh:
        fh.seek(offset)
        raw = fh.readline()
    row = next(csv.reader([raw.decode("utf-8", "replace")], delimiter=DELIM))
    return dict(zip(self.header, row))
```

**`csv.reader([одна_строка])`** — трюк. `csv.reader` принимает любой **итератор строк**,
не обязательно файл. Список из одной строки — валидный итератор. `next(...)` берёт
первую (и единственную) разобранную запись. Так мы используем полноценный парсер CSV
(кавычки, экранирование, разделители внутри кавычек) на одной строке, не открывая
файл как CSV целиком.

Тот же приём в конструкторе для заголовка (строка 84) и в `tsc_label.py:102-105`.

**`dict(zip(self.header, row))`** — сшить два списка в словарь. `zip` останавливается
по **короткому** из них: если в строке меньше колонок, чем в заголовке, лишние
ключи просто не появятся (а `KeyError` потом гасит `column()`, который возвращает
`default`). Если нужно поведение «упасть при рассинхроне», в Python 3.10+ есть
`zip(a, b, strict=True)`.

```python
def get(self, pn: str):
    key = pn.strip().upper().encode("utf-8")
    if not key:
        return None
    for found, offset in self._iter_from(key, 1):
        if found.encode("utf-8") == key:
            return self._row_at(offset)
    return None
```

`_lower_bound` даёт первую запись `>= key`. Если она **равна** ключу — попали;
если больше — такого номера нет. Отсюда `limit=1` и явная проверка на равенство.
Нормализация ключа (`strip().upper()`) должна совпадать с нормализацией при сборке
индекса (`build_index`, строка 61: `.strip().strip(b'"').upper()`). Это негласный контракт
между двумя функциями — если в одной поменять правило, вторую надо править синхронно.

```python
def suggest(self, prefix: str, limit: int = 12):
    ...
    for pn, _ in self._iter_from(key, limit * 4):
        if not pn.encode("utf-8").startswith(key):
            break
```

Поиск по префиксу — прямое следствие сортировки: все номера с общим префиксом лежат
подряд. Идём от границы вправо, пока префикс совпадает, `break` на первом несовпадении.
Запас `limit * 4` — на случай дублей номеров в каталоге (один номер может встречаться
в нескольких исходных каталогах).

#### Блок 6. Маппинг колонок (строки 171–192)

```python
def column(row: dict, key_part: str, default: str = "") -> str:
    for k, v in row.items():
        if key_part in k:
            return (v or "").strip()
    return default
```

Заголовки CSV выглядят как `Каталожный номер (part_number)` — русское название плюс
английский идентификатор в скобках. Код ищет колонку **по фрагменту** имени, а не по
точному совпадению, чтобы пережить косметические правки заголовка.

`(v or "")` — идиома «дефолт для `None` и пустой строки разом»: `or` возвращает
первый истинный операнд, а `None`, `""` и `0` — ложные. Здесь спасает от
`AttributeError: 'NoneType' object has no attribute 'strip'`.

**Слабое место, о котором стоит знать.** Поиск по подстроке возвращает **первое**
совпадение в порядке словаря (= порядке колонок в файле). Если в каталоге появится
колонка вроде `replaced_part_number`, а она окажется левее `part_number`,
то `column(row, "part_number")` вернёт не то. Устойчивее было бы искать точное
совпадение по содержимому скобок:

```python
import re
def column(row, key, default=""):
    for k, v in row.items():
        if re.search(rf"\({re.escape(key)}\)\s*$", k):
            return (v or "").strip()
    return default
```

Сейчас это не баг, а зависимость от формы заголовка — стоит держать в голове
при следующей выгрузке каталога.

### Key Technical Concepts

#### Концепт 1: Memory-mapped I/O (`mmap`)

**Что**: файл отображается в виртуальную память процесса. Обращение к байту
`mm[N]` — это обычное чтение памяти; если страницы нет в RAM, процессор ловит
page fault, ядро подгружает 4 КБ с диска и возвращает управление. Прозрачно для кода.

**Почему здесь**: 66 МБ индекса, из которых двоичный поиск реально трогает ~26 страниц.
Читать файл целиком (`read()`) — 66 МБ в кучу процесса на каждый старт.
`seek`/`read` вручную — то же самое, но с ручным управлением буфером и лишним
системным вызовом на каждое сравнение.

**Когда применять**: read-only данные больше памяти, случайный доступ, много процессов
на один файл (страницы шарятся между ними через page cache — очень дёшево).

**Trade-offs**:
* Плюсы: нулевой прогрев, память платит ОС и умеет её отдать, случайный доступ на скорости RAM после первого обращения, страницы шарятся между процессами.
* Минусы: файл нельзя усечь или перезаписать, пока отображение живо (отсюда `close()` перед пересборкой); на 32-битных системах упирается в адресное пространство; на сетевых ФС (NFS/SMB) поведение непредсказуемо; при обращении к «дырке» в файле процесс получает `SIGBUS`, а не исключение.

**Альтернативы**:
* `open()` + `seek()`/`read()` — универсальнее, работает на любых ФС, но каждое сравнение = системный вызов.
* Полная загрузка в память — быстрее при многократном полном обходе, невозможна при данных > RAM.
* `sqlite3` с индексом по колонке — даёт произвольные запросы, транзакции, но требует импорта данных и второго большого файла.

**Что нужно знать, чтобы это понять**:
* Виртуальная память и страницы — что адрес в процессе не равен адресу в RAM.
* Page cache — ОС и так кэширует файлы; `mmap` просто даёт к этому кэшу прямой доступ.
* Файловый дескриптор — что `open()` возвращает не только питон-объект, но и число, живущее в ядре.

#### Концепт 2: Двоичный поиск по записям переменной длины

**Что**: классический бинпоиск требует индексируемого массива — «дай мне i-й элемент
за O(1)». В текстовом файле элементы (строки) разной длины, i-й элемент так не достать.
Решение: адресоваться **байтами**, а после каждого прыжка «прилипать» к ближайшей
границе записи слева.

**Почему здесь**: строит индекс `sort(1)`, у которого нет и не может быть
фиксированной ширины записи. Вариант «выровнять все записи по 32 байта» дал бы
честный `O(1)`-доступ, но раздул бы индекс и потребовал бы обрезать длинные номера.

**Когда применять**: любой отсортированный line-oriented файл — логи, дампы,
`.tsv` выгрузки, словари.

**Trade-offs**:
* Плюсы: работает поверх обычного текстового файла, который можно посмотреть `less`, отсортировать `sort`, проверить `grep`.
* Минусы: инвариант «`lo` — начало строки» легко сломать при правке (см. ветку `if start < lo`), и поломка проявляется как редкий неверный ответ, а не как падение. Такой код стоит покрывать тестом на границы: первая запись, последняя, ключ меньше всех, ключ больше всех, ключ между двумя.

**Альтернативы**:
* Записи фиксированной ширины → настоящий бинпоиск по `mm[i*W:(i+1)*W]`, проще и быстрее, но жёсткая схема.
* Отдельный «индекс индекса»: массив смещений строк → тоже настоящий `O(1)`, но это ещё один файл.
* `bisect` над списком в памяти — если данные влезают.

**Что нужно знать**:
* Инварианты цикла — почему `lo`/`hi` всегда на границах записей.
* `lower_bound` vs `upper_bound` — семантика границ, а не «найдено/не найдено».
* Лексикографический порядок байтов vs порядок символов Unicode.

#### Концепт 3: Локаль и порядок сортировки (`LC_ALL=C`)

**Что**: локаль (`LC_COLLATE`) задаёт правила сравнения строк для `sort`, `strcoll`,
`ORDER BY` в БД и т.д. В `C`/`POSIX` сравнение побайтовое. В `en_US.UTF-8` — по правилам
Unicode Collation Algorithm: регистр и пунктуация вторичны, `"a-1" < "a1" < "A2"`
может выглядеть совсем не как порядок байтов.

**Почему здесь**: `sort` сортирует, `_lower_bound` ищет. Если у них разный компаратор,
двоичный поиск теряет предусловие «массив отсортирован» и возвращает мусор
для части ключей. Каталожные номера как раз содержат дефисы и смесь регистров —
именно тот случай, где локали расходятся.

**Когда применять**: **всегда** форсируйте `LC_ALL=C`, когда сортируете данные,
которые потом будете читать программой, а не человеком. И наоборот — для вывода
пользователю нужна его локаль.

**Trade-offs**: `C` даёт воспроизводимость на любой машине, но «неправильный»
для человека порядок (`Z` раньше `a`, кириллица после латиницы).

**Альтернативы**: отсортировать в Python (`sorted(..., key=...)`) — компаратор
гарантированно тот же, но память; или хранить ключи в фиксированной нормализованной
форме (uppercase ASCII), тогда локали расходятся меньше — но «меньше» это не «никогда».

**Что нужно знать**: переменные окружения и их наследование подпроцессами;
разница `LC_ALL` / `LC_COLLATE` / `LANG` (`LC_ALL` перебивает всё).

#### Концепт 4: Генераторы Python

**Что**: функция с `yield` при вызове возвращает объект-генератор. Тело исполняется
лениво, по одному шагу на `next()`; локальные переменные и точка исполнения
сохраняются между шагами.

**Почему здесь**: `get()` нужен один элемент, `suggest()` — до дюжины, и оба должны
уметь остановиться, не читая дальше.

**Когда применять**: обход большого/бесконечного источника, конвейеры обработки,
любой код, где потребитель может остановиться раньше.

**Trade-offs**:
* Плюсы: постоянная память, ленивость, естественный `break`.
* Минусы: одноразовость (второй раз по тому же объекту не пройти), нельзя `len()`, отладка сложнее — стек в момент ошибки «внутри» генератора.

**Альтернативы**: вернуть список (проще, дороже), `itertools.islice(generator, n)`
вместо ручного `limit`, `yield from` для делегирования вложенному генератору.

**Что нужно знать**: протокол итератора (`__iter__` / `__next__` / `StopIteration`);
что `for` — это синтаксический сахар над ним.
