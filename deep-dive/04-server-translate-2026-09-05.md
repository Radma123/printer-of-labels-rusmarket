## Overview

### Что этот код делает

`server.py` — локальный HTTP-сервер на стандартной библиотеке. Слушает
`127.0.0.1:8765`, отдаёт статику из `label_app/static/` и восемь API-эндпоинтов:
статус, геометрия макета, поиск детали, автодополнение, штрихкод, превью (PNG
и JSON+рамки), печать, сохранение TSPL. Плюс фоновая сборка индекса каталога.

`translate.py` — перевод наименования детали EN → IT/FR/DE/ES/PT через бесплатный
API MyMemory, с дисковым кэшем и параллельными запросами.

Ноль сторонних зависимостей, кроме Pillow. Ни Flask, ни FastAPI, ни requests.

### Почему выбран такой подход

**Почему не Flask/FastAPI.** Приложение ставится на рабочий Mac кладовщика
скриптом `launch.sh`, который создаёт `.venv` и ставит зависимости. Каждая
зависимость — это шанс, что установка не пройдёт: нет сети, конфликт версий,
корпоративный прокси. `http.server` есть в любом Python 3. Восемь эндпоинтов
и один потребитель (свой же фронтенд) — фреймворк тут даёт роутинг и валидацию,
которых на таком объёме не жалко написать руками (`do_GET` — это цепочка `if`
на 70 строк).

Обратная сторона честно есть: нет валидации входа, нет middleware, роутинг —
линейный поиск по строке пути. На восьми ручках это дешевле фреймворка;
на сорока было бы наоборот.

**Почему `ThreadingMixIn`, а не asyncio.** Вся тяжёлая работа —
блокирующая и CPU-bound (`render` в Pillow, `subprocess` к `lp`, чтение CSV).
Асинхронность тут не даёт ничего: `await` не ускоряет рендер картинки.
Потоки же решают конкретную проблему — пока `/api/preview` рисует картинку
200 мс, `/api/status` должен отвечать.

**Почему MyMemory, а не DeepL/Google.** Не нужен ключ API. Приложение
разворачивается копированием папки; требовать «зарегистрируйтесь и вставьте
токен» — это шаг, на котором установка останавливается. Цена: качество
машинного перевода средненькое и лимит 5000 символов в сутки (50 000 с указанным
email). Отсюда две вещи в коде: **кэш на диске** (повторная печать той же детали
не тратит лимит и работает офлайн) и **редактируемые поля** во фронтенде —
пользователь всегда может поправить перевод руками.

### Контекст

Такая архитектура — «однопользовательский локальный сервер как замена GUI» —
хороша, когда: интерфейс нужен богатый (браузер даёт его бесплатно), пользователь
один, данные не покидают машину, а установка должна быть тривиальной.
Так устроены Jupyter, Syncthing, локальные админки. Плохо подходит для
многопользовательского сценария: здесь нет ни аутентификации, ни ограничения
скорости, ни изоляции — и не должно быть, потому что сервер слушает только loopback.

`label_app/` — **не пакет**: в нём нет `__init__.py`. Модули импортируются
как верхнеуровневые (`import catalog`, а не `from label_app import catalog`),
и `render.py` тоже делает `import barcode as bc` (строка 18). Чтобы это работало
при запуске `python3 label_app/server.py` из любой директории, путь к папке
добавляется в `sys.path` вручную.

**`sys.path`** — список директорий, в которых Python ищет модули при `import`.
`insert(0, ...)` кладёт в начало, то есть с наивысшим приоритетом.

Побочный эффект, о котором стоит знать: имена вроде `catalog`, `render`, `translate`
теперь **перекрывают** одноимённые модули, если такие появятся в стандартной
библиотеке или в установленных пакетах. Здесь это осознанный размен: цена —
теоретический конфликт имён, выигрыш — приложение запускается любой командой
из любой папки.

**`# noqa: E402`** — подавление предупреждения линтера. E402 это «module level
import not at top of file»: PEP 8 требует все импорты в начале, а здесь между
ними стоит `sys.path.insert`. Правило нарушено осознанно (иначе импорты
не найдут модули), поэтому оно глушится точечно, с указанием кода —
а не глобально в конфиге линтера.

Правильный способ решить это без хака — сделать `label_app` пакетом
(`__init__.py` + относительные импорты `from . import catalog`) и запускать
`python3 -m label_app.server`. Тогда `sys.path` трогать не нужно. Выбранный
вариант проще для «запусти файл и всё работает».

```python
CSV_PATH = os.environ.get(
    "LABEL_CSV",
    os.path.join(os.path.dirname(HERE), "CNH_All_Parts_not-Full_20Cols.csv"))
PORT = int(os.environ.get("LABEL_PORT", "8765"))
```

**`os.environ.get(key, default)`** — конфигурация через переменные окружения
с разумным дефолтом. Пять таких точек по проекту (`LABEL_CSV`, `LABEL_PORT`,
`LABEL_FONT`, `LABEL_FONT_MONO`, `LABEL_NO_BROWSER`, `MYMEMORY_EMAIL`).
Это самый дешёвый механизм конфигурации: не нужен парсер конфигов, не нужен
файл настроек, значение легко переопределить на один запуск
(`LABEL_PORT=9000 python3 label_app/server.py`).

#### Блок 2. Ленивое открытие каталога и блокировка (строки 45–60)

```python
_cat = None
_cat_lock = threading.Lock()

def get_catalog():
    """Каталог открывается лениво: без CSV приложение всё равно работает."""
    global _cat
    with _cat_lock:
        if _cat is None and os.path.exists(CSV_PATH):
            _cat = catalog.Catalog(CSV_PATH)
        return _cat
```

Сервер многопоточный, значит `get_catalog()` может быть вызван из двух потоков
одновременно. Без блокировки оба увидели бы `_cat is None` и создали **два**
объекта `Catalog`, каждый со своим `mmap` — утечка файлового дескриптора
и лишнее отображение.

**`threading.Lock`** — примитив взаимного исключения. `with _cat_lock:` — это
`acquire()` на входе и `release()` в `finally` на выходе, даже при исключении.
Ручной вариант (`lock.acquire()` / `lock.release()`) опасен именно тем, что
при исключении между ними блокировка не освободится и сервер повиснет намертво.

Оговорка про GIL: в CPython глобальная блокировка интерпретатора не спасает
от таких гонок. GIL гарантирует атомарность **отдельных байткод-операций**,
но `if _cat is None` и `_cat = Catalog(...)` — это разные операции, между ними
поток может быть вытеснен. GIL защищает внутренности интерпретатора, а не логику
вашей программы.

Обратите внимание, что `return _cat` находится **внутри** `with`. Это не
обязательно (значение уже вычислено), но так очевиднее, что за пределами
блокировки ничего не происходит.

#### Блок 3. Фоновая задача и прогресс (строки 47, 63–80)

```python
_index_state = {"running": False, "done": 0, "total": 0, "error": ""}

def build_index_async():
    def work():
        _index_state.update(running=True, done=0, error="",
                            total=os.path.getsize(CSV_PATH))
        try:
            catalog.build_index(
                CSV_PATH,
                progress=lambda done, total: _index_state.update(done=done, total=total))
        except Exception as exc:                             # noqa: BLE001
            _index_state["error"] = str(exc)
        finally:
            _index_state["running"] = False
            global _cat
            with _cat_lock:
                if _cat is not None:
                    _cat.close()
                _cat = None
    threading.Thread(target=work, daemon=True).start()
```

Сборка индекса — две минуты. Держать HTTP-запрос открытым две минуты нельзя:
браузер отвалится по таймауту, а пользователь не увидит прогресса. Классическое
решение — **задача в фоне + отдельная ручка статуса**, которую фронтенд опрашивает
(`app.js:657`, `setInterval` раз в секунду).

**Вложенная функция `work`** — замыкание, видит `CSV_PATH` и `_index_state`
из внешней области. Ей не нужны аргументы, поэтому `Thread(target=work)` без `args`.

**`daemon=True`** — поток-демон не удерживает процесс от завершения. Без него
`Ctrl+C` в терминале не убил бы сервер, пока не закончится сборка индекса.
Обратная сторона: демон обрывается **на полуслове** при выходе. Здесь это
приемлемо — `build_index` пишет во временный файл (`.tmp`), так что оборванная
сборка не оставит битый индекс, максимум мусорный `.tmp`.

**`finally` с `global _cat`** — критичный момент. После пересборки индекса старый
`mmap` указывает на **перезаписанный файл**. Отображение переживает перезапись
и продолжает отдавать старые байты (или, если файл усечён, процесс получит `SIGBUS`).
Поэтому объект каталога закрывается и обнуляется — следующий `get_catalog()`
создаст новый.

**`except Exception` вместо `except:`** — голый `except:` ловит ещё и
`KeyboardInterrupt`, `SystemExit`, `GeneratorExit` (они наследуются от
`BaseException`, а не от `Exception`). В фоновом потоке это означало бы,
что поток проглатывает сигнал завершения. `# noqa: BLE001` — подавление правила
«blind except»: здесь широкий перехват намеренный, потому что упасть фоновый
поток не должен ни при какой ошибке, а сообщение нужно донести до UI через
`_index_state["error"]`.

**Про гонки на `_index_state`**: словарь читается из потоков-обработчиков HTTP
(`/api/status`) и пишется из фонового. Блокировки нет. Это работает, потому что
присваивание значения по ключу словаря — атомарная байткод-операция в CPython,
и здесь нет составных инвариантов (никто не читает `done` и `total` так, чтобы
их рассогласование сломало логику — максимум прогресс-бар дёрнется на процент).
Осознанный компромисс, но стоит понимать, что он опирается на деталь реализации
CPython, а не на гарантии языка.

#### Блок 4. Локали и `lpstat` (строки 49–93)

```python
_CUPS_ENV = dict(os.environ, LC_ALL="C", LANG="C")

def printers():
    # lpstat -p / -a печатают локализованный текст статуса ("принтер X
    # свободен") даже с LC_ALL=C — на macOS lpstat берёт язык из системных
    # настроек, а не из окружения процесса. -e — единственный режим, где
    # выводятся только имена очередей, без переводимого текста вокруг.
    try:
        out = subprocess.run(["lpstat", "-e"], capture_output=True, text=True,
                             timeout=10, env=_CUPS_ENV).stdout
    except Exception:                                        # noqa: BLE001
        return []
    return [ln.strip() for ln in out.splitlines() if ln.strip()]
```

Комментарий здесь ценнее кода: это **зафиксированный результат отладки**.

История: старый `tsc_label.py:283-289` парсит `lpstat -p` и берёт второе слово
из строк, начинающихся с `"printer "`. На русской macOS `lpstat` печатает
«принтер TSC_TE200 свободен», строка не начинается с `"printer "`, и список
очередей оказывается пустым — приложение сообщает «принтеров нет» при
подключённом принтере.

Первая попытка починки — форсировать `LC_ALL=C`. Не сработало: на macOS `lpstat`
берёт язык из системных настроек (`AppleLanguages`), а не из переменных окружения
процесса. Рабочее решение — режим `-e`, который печатает **только имена очередей**,
без переводимого текста вокруг. Парсить нечего, значит и ломаться нечему.

Урок общего характера: **не парсите человекочитаемый вывод CLI**. Ищите
машиночитаемый режим (`--json`, `--porcelain` у git, `-e` здесь) или библиотеку.
Если машинного режима нет — минимизируйте предположения о формате: здесь
финальная версия делает лишь `splitlines()` и `strip()`.

`_CUPS_ENV` всё равно оставлен и используется в `/api/print` (строка 263) —
на `lp` локаль влияет предсказуемо, и сообщения об ошибках приходят по-английски,
что для показа в UI и для гугления лучше.

**`subprocess.run(..., capture_output=True, text=True, timeout=10)`**:
* `capture_output=True` — эквивалент `stdout=PIPE, stderr=PIPE`;
* `text=True` — декодировать вывод в `str` (иначе `bytes`);
* `timeout=10` — при зависании `lpstat` (бывает, если принтер отвалился по сети) поднимется `TimeoutExpired`, а не вечное ожидание. Таймаут на внешний процесс — обязателен, если результат нужен в HTTP-обработчике.

#### Блок 5. Базовый обработчик (строки 96–129)

```python
class Handler(http.server.BaseHTTPRequestHandler):
    protocol_version = "HTTP/1.1"

    def _send(self, code, body: bytes, ctype="application/json; charset=utf-8"):
        self.send_response(code)
        self.send_header("Content-Type", ctype)
        self.send_header("Content-Length", str(len(body)))
        self.send_header("Cache-Control", "no-store")
        self.end_headers()
        self.wfile.write(body)
```

**`protocol_version = "HTTP/1.1"`** — атрибут класса, не экземпляра. По умолчанию
`BaseHTTPRequestHandler` работает по HTTP/1.0, то есть **закрывает соединение
после каждого ответа**. С HTTP/1.1 включается keep-alive: одно TCP-соединение
обслуживает много запросов. При дебаунсе превью в 110 мс во время перетаскивания
это заметная экономия — без keep-alive каждое движение мыши открывало бы
новое соединение.

Условие корректности keep-alive: **обязателен точный `Content-Length`**
(или chunked transfer). Без него клиент не знает, где кончается ответ, и
соединение зависает. Отсюда `send_header("Content-Length", ...)` в единственной
функции отправки — все ответы идут через `_send`, поэтому забыть невозможно.
Это и есть причина, по которой отправка централизована.

**`Cache-Control: no-store`** — превью и статус меняются на каждый запрос;
кэш браузера здесь только мешал бы (особенно `/api/preview.png` с параметрами
в URL, который браузер охотно закэшировал бы).

```python
def json(self, obj, code=200):
    self._send(code, json.dumps(obj, ensure_ascii=False).encode("utf-8"))
```

**`ensure_ascii=False`** — по умолчанию `json.dumps` экранирует все не-ASCII
символы в `\uXXXX`. Русский текст превратился бы в `"Найд..."` —
валидный JSON, но втрое больше и нечитаемый в отладке. С `False` — UTF-8 как есть,
и заголовок `charset=utf-8` уже стоит.

```python
def log_message(self, fmt, *args):                       # тише в консоли
    pass
```

Переопределение метода базового класса пустым телом. По умолчанию
`BaseHTTPRequestHandler` пишет строку в stderr на **каждый** запрос; при
дебаунсе превью это несколько строк в секунду, и `logs/app.log` за день
разрастается на десятки мегабайт. Сигнатура `(self, fmt, *args)` повторяет
базовую — так метод остаётся совместимым, даже если библиотека где-то вызовет
его с аргументами.

#### Блок 6. Раздача статики и обход пути (строки 118–129)

```python
def serve_static(self, rel):
    path = os.path.normpath(os.path.join(STATIC, rel.lstrip("/")))
    if not path.startswith(STATIC) or not os.path.isfile(path):
        return self.fail("не найдено", 404)
```

**Path traversal** — классическая атака: запрос `GET /../../../../etc/passwd`.
Защита в два шага:

1. **`os.path.normpath`** схлопывает `..` и `.`: `static/../../etc/passwd` → `/etc/passwd`.
   Нормализация обязана быть **до** проверки — иначе `startswith` увидит строку,
   начинающуюся с `STATIC`, а реальный путь после разрешения `..` окажется снаружи.
2. **`startswith(STATIC)`** — результат должен остаться внутри папки статики.

`rel.lstrip("/")` — убрать ведущие слэши, чтобы `os.path.join` не воспринял
путь как абсолютный (`os.path.join("/a", "/etc")` даёт `"/etc"` — частая ловушка).

**Известная слабость этой проверки.** `STATIC` — путь без завершающего разделителя,
поэтому `startswith` пропустит **соседнюю папку с общим префиксом**:
`/path/to/static_secrets/x` начинается с `/path/to/static`. Здесь это недостижимо
(создать такую папку может только владелец машины, а сервер слушает loopback),
но приём стоит знать в правильной форме:

```python
import os
base = os.path.realpath(STATIC)
path = os.path.realpath(os.path.join(base, rel.lstrip("/")))
if os.path.commonpath([base, path]) != base:
    return self.fail("не найдено", 404)
```

`realpath` дополнительно разрешает симлинки — `normpath` этого не делает,
так что символическая ссылка внутри `static/` наружу текущую проверку обошла бы.
`commonpath` сравнивает по сегментам пути, а не по символам строки.

#### Блок 7. Роутинг (строки 132–206)

```python
def do_GET(self):
    url = urllib.parse.urlparse(self.path)
    q = urllib.parse.parse_qs(url.query)
    one = lambda k, d="": (q.get(k) or [d])[0]           # noqa: E731

    if url.path in ("/", "/index.html"):
        return self.serve_static("index.html")
    if not url.path.startswith("/api/"):
        return self.serve_static(url.path)

    if url.path == "/api/status":
        return self.json({...})
```

Роутинг — цепочка `if` с ранним `return`. `return self.json(...)` возвращает
`None` (метод `json` ничего не возвращает), но конструкция «`return` вызов»
читается как «ответили и вышли» и экономит уровень вложенности.

**`parse_qs`** возвращает `dict[str, list[str]]` — список, потому что параметр
может повторяться (`?a=1&a=2` → `{"a": ["1", "2"]}`). Отсюда хелпер `one`,
который берёт первое значение или дефолт: `(q.get(k) or [d])[0]`.
`q.get(k)` даёт `None` при отсутствии ключа, `None or [d]` → `[d]`, берём `[0]`.

**`# noqa: E731`** — правило «do not assign a lambda expression, use a def».
PEP 8 не любит `f = lambda ...`, потому что у такой функции имя `<lambda>`
в трассировках. Здесь это однострочный локальный хелпер, читаемость выигрывает,
правило глушится точечно.

```python
if url.path == "/api/part":
    cat = get_catalog()
    if cat is None:
        return self.fail(f"CSV не найден: {CSV_PATH}", 503)
    if not catalog.index_is_fresh(CSV_PATH):
        return self.fail("индекс каталога ещё не построен", 409)
    row = cat.get(one("pn"))
    if row is None:
        return self.json({"found": False, "suggest": cat.suggest(one("pn"), 8)})
```

**Осмысленные HTTP-коды**, а не «всё 500»:
* `503 Service Unavailable` — сервис временно не может работать (нет CSV). Семантически верно: проблема во внешнем ресурсе, а не в запросе.
* `409 Conflict` — состояние сервера не позволяет выполнить запрос (индекс не построен). Фронтенд по этому коду показывает кнопку «Собрать индекс».
* «Не найдено» — **не** 404, а `200` с `{"found": False}`. Правильно: 404 означает «нет такого ресурса `/api/part`», а здесь ресурс есть и он честно отвечает «детали в каталоге нет». Плюс в том же ответе приезжают похожие номера — полноценный полезный ответ, а не ошибка.

```python
if url.path == "/api/preview.png":
    data = json.loads(one("data", "{}"))
    scale = max(1, min(6, int(one("scale", "3"))))
```

Два места без защиты: `json.loads` бросит `JSONDecodeError`, а `int()` —
`ValueError`, если в query придёт мусор. Исключение в обработчике
`BaseHTTPRequestHandler` даёт трассировку в лог и **оборванный ответ** —
браузер увидит сломанное соединение без объяснений. В `do_POST` это уже
обработано (строки 212–215 и 238–241), в этой ветке — нет. Ручка вызывается
только своим же фронтендом (`app.js:626`, кнопка «сохранить PNG»), так что
на практике не стреляет, но это неравномерность в обработке ошибок.

`max(1, min(6, ...))` — clamp масштаба. Ограничение сверху важно не косметически:
`scale=50` — это картинка 14000×19700 пикселей и несколько гигабайт памяти.
Даже на локальном сервере параметры из URL стоит зажимать.

#### Блок 8. Печать (строки 256–268)

```python
if url.path == "/api/print":
    queue = (body.get("printer") or "").strip()
    if not queue:
        return self.fail("не выбран принтер")
    copies = max(1, min(999, int(body.get("copies") or 1)))
    job = render.build_tspl(body.get("label") or {}, copies)
    res = subprocess.run(["lp", "-d", queue, "-o", "raw", "-"],
                         input=job, capture_output=True, env=_CUPS_ENV)
    if res.returncode != 0:
        return self.fail(res.stderr.decode("utf-8", "replace").strip()
                         or "CUPS отклонил задание", 500)
```

**`lp -o raw -`** — ключевая команда всего проекта. `-o raw` говорит CUPS
«не пропускай через фильтры драйвера, отправь байты в устройство как есть».
Именно это позволяет говорить с принтером на TSPL, минуя PPD и драйверы.
Финальный `-` — читать данные со stdin.

**`subprocess.run(cmd, input=job)`** — `input` принимает `bytes` (потому что
не задан `text=True`) и передаёт их в stdin процесса, дожидаясь завершения.
Это удобная обёртка над `Popen` + `communicate()`.

**Список аргументов, а не строка** — `["lp", "-d", queue, ...]`, а не
`f"lp -d {queue} ..."` с `shell=True`. Разница принципиальная: со списком
аргументы уходят в `execve` как есть, оболочка не участвует, и имя очереди
с пробелом или `;` не превращается в инъекцию команд. Правило:
**`shell=True` только когда действительно нужен shell**, и никогда — с данными
из запроса.

**Ошибка CUPS передаётся пользователю дословно** (`res.stderr`). Для локального
инструмента это правильно: «lp: Error - unable to access "TSC_TE200"» гуглится
и чинится, а «ошибка печати» — нет. Для публичного сервиса так делать нельзя —
stderr может раскрыть пути и конфигурацию.

`... .strip() or "CUPS отклонил задание"` — снова идиома `or` для дефолта:
если `lp` вернул ненулевой код, но ничего не написал в stderr, покажем хоть что-то.

#### Блок 9. Многопоточный сервер (строки 281–298)

```python
class Server(socketserver.ThreadingMixIn, http.server.HTTPServer):
    daemon_threads = True
    allow_reuse_address = True
```

**Mixin через множественное наследование.** `ThreadingMixIn` переопределяет
`process_request` так, чтобы каждый запрос обрабатывался в новом потоке.
Порядок баз важен: mixin **слева**, чтобы его методы имели приоритет в MRO
(method resolution order — порядок, в котором Python ищет атрибут по цепочке
наследования). `class Server(HTTPServer, ThreadingMixIn)` не сработал бы:
`HTTPServer.process_request` нашёлся бы первым.

**`daemon_threads = True`** — потоки-обработчики не удерживают процесс.
Без этого `Ctrl+C` ждал бы завершения всех висящих запросов.

**`allow_reuse_address = True`** — устанавливает `SO_REUSEADDR` на сокете.
Без него после остановки сервера порт остаётся в состоянии `TIME_WAIT`
на ~60 секунд, и рестарт падает с «Address already in use». Для приложения,
которое перезапускают командой `launch.sh restart`, это обязательно.

```python
if os.environ.get("LABEL_NO_BROWSER") != "1":
    threading.Timer(0.6, lambda: webbrowser.open(url)).start()
with Server(("127.0.0.1", PORT), Handler) as httpd:
    try:
        httpd.serve_forever()
    except KeyboardInterrupt:
        print("\nостановлено")
```

**`threading.Timer`** — поток, который спит заданное время и вызывает функцию.
Здесь: открыть браузер через 0.6 секунды. Почему с задержкой — `serve_forever()`
вызывается ниже, и если открыть браузер до него, первый запрос может прийти
раньше, чем сокет начнёт слушать. Задержка — простое решение; более честное —
открывать после того, как сокет привязан (`Server(...)` уже сделал bind, так что
таймер можно было бы заменить на прямой вызов внутри `with` до `serve_forever`).

**`with Server(...) as httpd`** — `socketserver.BaseServer` поддерживает протокол
контекстного менеджера, `__exit__` вызывает `server_close()` и освобождает сокет.

**`LABEL_NO_BROWSER`** — переменная для запуска без открытия браузера
(отладка, автозапуск). Хорошая привычка: любое «удобное» побочное действие
должно иметь выключатель.

#### Блок 10. Кэш с атомарной записью (строки 34–49)

```python
def _save_cache() -> None:
    tmp = CACHE_PATH + ".tmp"
    with open(tmp, "w", encoding="utf-8") as fh:
        json.dump(_cache, fh, ensure_ascii=False, indent=0, sort_keys=True)
    os.replace(tmp, CACHE_PATH)
```

**Атомарная замена файла.** Если писать прямо в `CACHE_PATH` и процесс умрёт
на середине, кэш останется битым JSON — и следующий запуск не сможет его прочитать
(спасёт только `except` в `_load_cache`, который молча обнулит весь накопленный кэш).

`os.replace` — обёртка над системным `rename(2)`, который на одной файловой
системе **атомарен**: наблюдатель видит либо старый файл целиком, либо новый
целиком, никогда не промежуточное состояние. Отличие от `os.rename`: `os.replace`
работает одинаково на Windows (где `rename` падает, если цель существует).

Тот же приём — в `catalog.build_index` (`.tmp` → `sort -o idx`). Общее правило:
**любая запись файла, который кто-то может читать параллельно, должна идти
через временный файл и rename**.

`sort_keys=True` — детерминированный порядок ключей. Полезно, если файл
когда-нибудь попадёт под git: диффы станут осмысленными.
`indent=0` — переносы строк без отступов: файл читаемый глазом, но не раздутый.

#### Блок 11. Параллельные запросы (строки 95–122)

```python
fetched = {}

def worker(lang):
    try:
        fetched[lang] = _fetch(src, lang)
    except Exception as exc:                            # noqa: BLE001
        result["errors"][lang] = str(exc)

threads = [threading.Thread(target=worker, args=(l,)) for l in todo]
for t in threads:
    t.start()
for t in threads:
    t.join()
```

Пять языков — пять HTTP-запросов. Последовательно это 5 × ~500 мс ≈ 2.5 секунды.
Параллельно — примерно 500 мс, потому что задача **I/O-bound**: потоки почти всё
время ждут сеть, а не считают. GIL при ожидании ввода-вывода **освобождается**,
так что потоки в Python здесь дают настоящее ускорение (в отличие от CPU-bound
задач, где нужен `multiprocessing`).

Идиома **«запустить все, потом дождаться всех»**: два отдельных цикла.
Если объединить в один (`t.start(); t.join()`), получится последовательное
выполнение — частая ошибка.

**Обработка ошибок внутри `worker`.** Исключение в потоке не всплывает
в вызывающий код: поток просто умирает, и `Thread` об этом молчит.
Поэтому ошибка ловится внутри и складывается в `result["errors"][lang]`.
Отсюда же паттерн `if lang in fetched` ниже (строка 110): успех определяется
не по отсутствию исключения, а по **наличию результата**.

Результат частичный: если три языка перевелись, а два нет, вернутся три перевода
и два сообщения об ошибке. Фронтенд подсветит неудавшиеся строки красным
(`app.js:181`, класс `failed`), пользователь впишет их руками. Для инструмента,
где всё редактируемо, это правильнее, чем «всё или ничего».

**Современная альтернатива** — `concurrent.futures`, где сбор результатов
и ошибок встроен:

```python
from concurrent.futures import ThreadPoolExecutor

with ThreadPoolExecutor(max_workers=5) as pool:
    futures = {lang: pool.submit(_fetch, src, lang) for lang in todo}
for lang, fut in futures.items():
    try:
        result[lang] = fut.result()
        result["source"][lang] = "api"
    except Exception as exc:
        result["errors"][lang] = str(exc)
        result["source"][lang] = "error"
```

Короче, и исключение всплывает при `.result()` в вызывающем потоке —
не нужен ручной трюк с `fetched`.

```python
with _lock:
    cache[f"{key_base}|{lang}"] = text
...
if fetched:
    with _lock:
        _save_cache()
```

Блокировка вокруг записи в кэш. Строго говоря, присваивание по ключу словаря
атомарно и без неё; блокировка реально нужна для `_save_cache()` — там
`json.dump` **итерирует** словарь, и если параллельный поток вставит ключ
во время итерации, будет `RuntimeError: dictionary changed size during iteration`.
Сценарий достижим: два одновременных запроса `/api/translate` разных наименований.

#### Блок 12. Разбор ответа API (строки 52–68)

## Concepts Explained

### Design Patterns Used

| Паттерн | Где | Зачем |
|---|---|---|
| Lazy initialization + lock | `get_catalog` | Ресурс берётся при первом обращении, ровно один раз даже при гонке |
| Background task + polling status | `build_index_async` + `/api/status` | Двухминутная операция без блокировки HTTP-запроса |
| Cache-aside | `translate` (кэш → промах → API → запись в кэш) | Экономия лимита, работа офлайн для повторов |
| Atomic file replace | `_save_cache`, `build_index` | Читатель никогда не видит полуготовый файл |
| Fan-out / fan-in | пять потоков `worker` + `join` | I/O-bound задачи параллельно, время = максимум, а не сумма |
| Partial success | `result["errors"][lang]` | Три перевода лучше нуля; неудачные правятся руками |
| Configuration via environment | `LABEL_CSV`, `LABEL_PORT`, `MYMEMORY_EMAIL` | Настройка без файла конфигурации и без правки кода |
| Centralized response | всё через `_send` | `Content-Length` невозможно забыть, keep-alive не ломается |

### Key Technical Concepts

#### Концепт 1: Потоки в Python и GIL

**Что**: GIL (Global Interpreter Lock) — блокировка, из-за которой в CPython
одновременно исполняется байткод только одного потока. При системных вызовах
(сеть, диск) GIL **освобождается**, и другие потоки работают.

**Почему здесь**: `translate` — I/O-bound, потоки дают настоящее пятикратное
ускорение. `ThreadingMixIn` — тоже про I/O: пока один поток ждёт `lp` или пишет
ответ в сокет, другие обслуживают запросы. При этом рендер картинки (CPU-bound)
параллелизма не получает — два одновременных `/api/preview` будут считаться
по очереди. Здесь это неважно: пользователь один.

**Когда применять**: потоки — для I/O-bound; `multiprocessing` или C-расширения —
для CPU-bound; `asyncio` — для тысяч одновременных соединений.

**Trade-offs**:
* Плюсы: простая модель, разделяемая память, знакомый код.
* Минусы: гонки требуют дисциплины (`_cat_lock`); исключение в потоке не всплывает; отладка тяжелее; на CPU-bound выигрыша нет.

**Альтернативы**: `concurrent.futures.ThreadPoolExecutor` (те же потоки,
удобнее API — см. Блок 11); `asyncio` + `aiohttp` (эффективнее на сотнях
соединений, но требует асинхронного стека целиком); `multiprocessing`
(настоящий параллелизм для вычислений, дорогая передача данных).
Отдельно: в Python 3.13+ появился экспериментальный режим free-threaded
(без GIL) — стоит следить, но для этого проекта неактуально.

**Что нужно знать**:
* Гонка данных и что именно защищает `Lock`.
* Разница I/O-bound / CPU-bound — от неё зависит выбор инструмента.
* Что GIL защищает интерпретатор, а не логику программы.

#### Концепт 2: Кэш-aside с записью на диск

**Что**: приложение само проверяет кэш, при промахе идёт к источнику и кладёт
результат в кэш. Кэш — не прокси, а хранилище рядом.

**Почему здесь**: лимит 5000 символов в сутки и сеть, которой может не быть.
Каталог конечен, наименования повторяются (тысячи деталей — «OIL FILTER»),
переводы не устаревают. Идеальный случай для вечного кэша.

**Когда применять**: дорогой или лимитированный внешний вызов + стабильный
результат + приемлемость чуть устаревших данных.

**Trade-offs**:
* Плюсы: экономия лимита, работа офлайн, мгновенный ответ на повторе.
* Минусы: инвалидации нет — если MyMemory улучшит перевод, вы этого не увидите (отсюда флаг `refresh`, строка 71, и кнопка «перевести заново» в UI); файл растёт неограниченно; при параллельной записи нужен `os.replace`.

**Альтернативы**:
* `functools.lru_cache` — только в памяти, теряется при рестарте.
* `sqlite3` — если кэш вырастет до сотен тысяч записей: не нужно читать весь файл в память при старте.
* TTL в записи (`{"text": ..., "ts": ...}`) — если бы данные устаревали.

**Что нужно знать**: инвалидация кэша и почему её называют одной из двух
сложных задач в CS; атомарность `rename`; разница «кэш в памяти» / «кэш на диске».

#### Концепт 3: Границы доверия к внешнему API

**Что**: любой ответ чужого сервиса — недоверенные данные. HTTP 200 не значит
«успех», наличие поля не значит «поле осмысленно».

**Почему здесь**: MyMemory кладёт текст предупреждения **в то же поле**,
где должен быть перевод. Без проверки `"MYMEMORY WARNING" in out.upper()`
на этикетку уехала бы английская фраза про исчерпанный лимит — и была бы
физически напечатана.

**Когда применять**: всегда при работе с внешним API. Минимальный набор:
таймаут (`TIMEOUT = 12`, строка 60), проверка кода ответа, проверка формы
данных, проверка **содержимого** на известные сигнальные значения.

**Trade-offs**: проверки специфичны для конкретного API и ломаются при его
изменении. Здесь это принято: три строки против нечитаемой этикетки.

**Альтернативы**: схема валидации (`pydantic`, `jsonschema`) — оправданно
при сложном ответе; клиентская библиотека провайдера — если есть.

**Что нужно знать**: что `urlopen` **без `timeout` может висеть вечно**;
разница между ошибкой транспорта и ошибкой на уровне приложения;
почему нельзя доверять `Content-Type` и коду ответа как единственным индикаторам.

**Отдельно — приватность.** Наименования деталей уходят на сторонний сервис.
MyMemory в бесплатном режиме **добавляет переводы в свою публичную память
переводов**. Для номенклатуры запчастей это, скорее всего, безразлично, но
решение стоит принимать осознанно: если в наименования когда-нибудь попадут
внутренние обозначения или названия клиентов, они станут публичными.
Это тот случай, когда `MYMEMORY_EMAIL` в переменной окружения — не только
про лимит, но и про то, чтобы понимать, чьи данные куда идут.

#### Концепт 4: Локальный сервер как интерфейс приложения

**Что**: вместо нативного GUI — HTTP-сервер на loopback плюс браузер как
средство отображения.

**Почему здесь**: интерфейс требует превью, перетаскивания, ползунков,
автодополнения. На Tkinter это недели работы; в браузере — знакомые инструменты.
Плюс кросс-платформенность бесплатно.

**Когда применять**: инструмент для одного пользователя, богатый UI, данные
не должны покидать машину, установка должна быть простой. Так работают Jupyter,
Streamlit, Syncthing, локальные админки БД.

**Trade-offs**:
* Плюсы: мощный UI без GUI-фреймворка, работает везде, обновление интерфейса = обновление файла.
* Минусы: нужен браузер; окно не выглядит как нативное приложение (отсюда `.app`-обёртка в `build_app.sh`); **безопасность целиком на привязке к 127.0.0.1**.

**О безопасности подробнее.** Сервер слушает только loopback — из сети снаружи
он недоступен. Но у локальных серверов без аутентификации есть два известных вектора:
*(а)* другой процесс/пользователь на той же машине может обращаться к API
(здесь неважно — машина однопользовательская); *(б)* **DNS rebinding**: вредоносная
страница в браузере пользователя заставляет его резолвить свой домен в `127.0.0.1`
и обращаться к вашему API от имени браузера. Защита от второго — проверять
заголовок `Host` и отвергать всё, кроме `127.0.0.1:PORT` и `localhost:PORT`.
Это три строки в `_send`/`do_GET`; для внутреннего инструмента на изолированной
машине — уместный, но не обязательный шаг.

**Альтернативы**: Electron/Tauri (нативное окно + веб — тяжелее, но выглядит
как приложение); PyQt/Tkinter (нативно, но UI писать дольше); CLI
(см. `tsc_label.py` — проще некуда, но без превью).

**Что нужно знать**: loopback-интерфейс и почему `127.0.0.1` не то же самое,
что `0.0.0.0`; same-origin policy; keep-alive и `Content-Length`.

### Смежные концепции

- **ASGI/WSGI** — стандартные интерфейсы между сервером и приложением; понимание помогает увидеть, что именно даёт фреймворк поверх `http.server`.
- **Server-Sent Events / WebSocket** — заменили бы опрос `/api/status` при сборке индекса на push. Для одной операции раз в жизни установки — избыточно, но приём полезный.
- **`functools.lru_cache` и мемоизация** — тот же кэш, но в памяти; сравните с дисковым.
- **Backoff и retry** — чего в `_fetch` нет: одна сетевая ошибка = ошибка перевода. Для пяти параллельных запросов к бесплатному API это осознанно (ретраи быстрее сожгут лимит), но приём знать полезно.
- **Structured logging** — сейчас `log_message` отключён полностью; промежуточный вариант — логировать только ошибки и печать.


   Первый запуск идёт в сеть, второй — из `translation_cache.json`. Разница

3. **Убедитесь, что кэш действительно атомарен**: посмотрите, что файл
   `label_app/translation_cache.json` появляется целиком, а `.tmp` не остаётся:

   ```bash
   ls -la label_app/translation_cache.json*
   ```

4. **Глубже**: замените ручные потоки в `translate.py` на `ThreadPoolExecutor`
   (код в Блоке 11) — станет короче и исчезнет трюк с `fetched`. Затем добавьте
   проверку заголовка `Host` в `Handler` — три строки, закрывающие DNS rebinding.

5. **Осторожно с**:
   * привязкой к `0.0.0.0` вместо `127.0.0.1` — сервер без аутентификации станет доступен из сети;
   * `shell=True` в `subprocess` с данными из запроса — имя очереди приходит из HTTP;
   * снятием `max(1, min(6, scale))` — большой `scale` съест память;
   * возвратом `res.stderr` пользователю, если сервер когда-нибудь выйдет за пределы loopback;
   * `json.loads(one("data"))` в `/api/preview.png` — единственная ветка без обработки ошибок разбора;
   * добавлением ещё одного фонового потока без пересмотра `_index_state` — сейчас он опирается на атомарность операций CPython, а не на блокировку.
