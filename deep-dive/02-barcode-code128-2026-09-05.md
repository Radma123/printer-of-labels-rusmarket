## Overview

### Что этот код делает

Превращает строку (`"84565867"`, `"C5NNF892A"`) в **список ширин полос в модулях**:

```python
>>> pattern("84565867")
{'widths': [2,1,1,2,3,2,  1,1,2,2,3,2, ...], 'modules': 79}
```

`widths[0]` — чёрная полоса, дальше цвета чередуются. Ни картинки, ни SVG —
только числа. Кто хочет — рисует их прямоугольниками (`render.draw_barcode`),
кто хочет — считает суммарную ширину для валидации (`/api/barcode` → строка
статуса под полем ввода).

91 строка кода, ноль зависимостей.

### Почему выбран такой подход

Три альтернативы и почему их не взяли:

**1. Отдать штрихкод самому принтеру** (`BARCODE ... "128" ...` — так делает
старый `tsc_label.py:258`). Принтер рисует Code 128 своей прошивкой, кода писать
не надо вообще. Но тогда **превью в браузере не знает, какой ширины получатся полосы**:
прошивка сама выбирает режимы кодирования и ширину модуля. Превью и печать
разъезжаются, а вся идея этого приложения — «печатается ровно то, что видно на экране».

**2. Библиотека `python-barcode` / `treepoem`**. Работает, но добавляет зависимость,
которая тянет свои (`Pillow` уже есть, а вот у `treepoem` — Ghostscript). Отдаёт
готовую картинку или SVG, а нужен именно **список ширин**, чтобы рисовать полосы
в той же системе координат в миллиметрах, что и всё остальное на этикетке.

**3. Считать один раз и захардкодить.** Номера в каталоге разные, не вариант.

Собственная реализация выигрывает по одной конкретной причине: **одна раскладка
на всех потребителей**. `barcode.pattern()` вызывается и из `render.draw_barcode`
(PNG-превью и то, что уходит в TSPL), и из `/api/barcode` (валидация в UI).
Расхождение между превью и печатью физически невозможно — это один и тот же список чисел.

### Контекст: когда так пишут свой кодек

Реализовать спецификацию руками разумно, когда: формат маленький и стабильный
(Code 128 не менялся с 1981 года), нужен не «готовый результат», а **промежуточное
представление**, и цена зависимости выше цены 90 строк. Не разумно — для форматов
с историей багов и вариантов (QR, PDF417, DataMatrix): там ошибка коррекции,
маскирование и версии, и своя реализация будет молча выдавать нечитаемые коды.

#### Блок 1. Таблица шаблонов (строки 11–27)

```python
_PATTERNS = (
    "212222 222122 222221 121223 121322 131222 122213 122312 132212 221213 "
    "221312 231212 112232 122132 122231 113222 123122 123221 223211 221132 "
    ...
    "114131 311141 411131 211412 211214 211232 2331112"
).split()
```

Как читать одну запись: `"212222"` — это шесть чисел подряд: полоса шириной 2 модуля,
пробел 1, полоса 2, пробел 2, полоса 2, пробел 2. Всегда 3 полосы + 3 пробела = 11 модулей.
Отсюда второе имя стандарта — **Code 128 = «11 модулей на символ»**.

Индекс в списке = **значение символа Code 128**. `_PATTERNS[0]` — значение 0
(в режиме B это пробел, в режиме C — «00»), `_PATTERNS[103]` — START A и так далее.
Последний элемент `"2331112"` — **семь** цифр, 13 модулей: это STOP, единственный
символ с четырьмя полосами. Он нужен, чтобы сканер понимал, где конец, читая код
в любом направлении.

**Языковые детали:**

* **Неявная конкатенация строковых литералов.** Два строковых литерала подряд —
  даже на разных строках внутри скобок — склеиваются **на этапе компиляции**:

  ```python
  s = "abc" "def"          # -> "abcdef", никакого + в рантайме
  ```

  Это не оператор, а синтаксис. Работает только для литералов
  (`"abc" x` — синтаксическая ошибка). Здесь используется, чтобы разложить
  таблицу по 10 записей в строку — читается и диффается гораздо лучше, чем список
  из 107 элементов через запятую.

* **`.split()` без аргументов** — не то же самое, что `.split(" ")`. Без аргумента
  разделителем считается **любая последовательность пробельных символов**,
  а ведущие/хвостовые отбрасываются. Поэтому лишний пробел на стыке строк
  (в конце каждой строки литерала стоит `" "`) не создаёт пустых элементов.
  С `.split(" ")` это бы сломалось.

* **Кортеж vs список.** `_PATTERNS` — результат `.split()`, то есть список.
  Скобки вокруг литерала — это группировка, а не кортеж (кортеж требует запятой).
  Для константы неизменяемость была бы приятнее: `tuple((...).split())`.

**Проверка целостности таблицы** — полезная привычка при ручном переносе спецификации:

```python
assert len(_PATTERNS) == 107
assert all(sum(int(c) for c in p) == 11 for p in _PATTERNS[:106])
assert sum(int(c) for c in _PATTERNS[106]) == 13     # STOP
```

Три строки, которые ловят опечатку в таблице сразу, а не на физически напечатанной
этикетке, которую не читает сканер.

#### Блок 2. Константы режимов (строки 26–27)

```python
START_A, START_B, START_C, STOP = 103, 104, 105, 106
CODE_A, CODE_B, CODE_C = 101, 100, 99
```

Code 128 — кодировка с **переключением режимов**:

| Режим | Что кодирует | Плотность |
|---|---|---|
| A | ASCII 0–95: заглавные, цифры, пунктуация, управляющие | 1 символ = 11 модулей |
| B | ASCII 32–127: заглавные, **строчные**, цифры, пунктуация | 1 символ = 11 модулей |
| C | только пары цифр `00`–`99` | **2 цифры = 11 модулей** |

`START_*` — стартовый символ, он же объявляет начальный режим. `CODE_*` —
переключение режима посреди кода. Режим C вдвое плотнее — это и есть предмет
оптимизации в `encode`.

Множественное присваивание `A, B, C = 1, 2, 3` — это распаковка кортежа.
Справа сначала строится кортеж `(103, 104, 105, 106)`, потом раскладывается по именам.
Побочный эффект, который иногда удивляет: `a, b = b, a` меняет местами без временной
переменной именно потому, что правая часть вычисляется целиком до присваивания.

#### Блок 3. Выбор режима — `encode` (строки 30–65)

```python
def _digit_run(text: str, i: int) -> int:
    n = 0
    while i + n < len(text) and text[i + n].isdigit():
        n += 1
    return n
```

Сколько цифр подряд начиная с позиции `i`. `str.isdigit()` для одного символа —
проверка «это цифра». Осторожно: `isdigit()` истинен и для `"²"` (надстрочная двойка),
и для цифр других письменностей (`"٣"` — арабо-индийская тройка). Для строгой
ASCII-проверки надёжнее `ch in "0123456789"` или `ch.isascii() and ch.isdigit()`.
Здесь это не стреляет: непечатаемое всё равно упрётся в проверку диапазона ниже,
но знать про разницу стоит.

```python
while i < len(text):
    run = _digit_run(text, i)
    # Режим C вдвое плотнее, но пары цифр должны быть полными.
    use_c = run >= 4 if (i > 0 or run < len(text)) else run >= 2
    if use_c and run % 2:
        run -= 1
```

Это **эвристика выбора режима**, и она стоит подробного разбора.

Переключение в режим C стоит один символ (`CODE_C`, 11 модулей) — это цена
одной лишней цифры. Значит, переключаться выгодно, когда экономия больше цены:

* цепочка из 4 цифр в режиме B = 4 × 11 = 44 модуля;
* она же: `CODE_C` + 2 пары = 3 × 11 = 33 модуля. Выгода.
* цепочка из 2 цифр: B = 22, C = `CODE_C` + 1 пара = 22. Ничья, переключаться незачем.

Отсюда `run >= 4` в общем случае. **Исключение** — начало строки: там стартовый
символ нужен в любом случае, `START_C` вместо `START_B` бесплатен. Поэтому если
**вся строка** состоит из цифр (`i == 0 and run == len(text)`), порог опускается
до `run >= 2`. Именно этот случай и есть типичный каталожный номер CNH — `"84565867"`,
восемь цифр, кодируется четырьмя символами вместо восьми.

**Разбор условия по частям.** `use_c = X if cond else Y` — тернарный оператор.
Читается «X, если cond, иначе Y» (порядок непривычный по сравнению с C-подобным
`cond ? X : Y`). Условие здесь:

```python
(i > 0 or run < len(text))
```

Ложно, только когда `i == 0` **и** `run == len(text)` — то есть «мы в начале и вся
строка целиком цифровая». Ровно тот особый случай. Двойное отрицание в голове читается
тяжело; понятнее было бы:

```python
whole_string_is_digits = (i == 0 and run == len(text))
use_c = run >= 2 if whole_string_is_digits else run >= 4
```

Тот же смысл, но без мысленной инверсии.

`if use_c and run % 2: run -= 1` — в режиме C кодируются **пары**, нечётный хвост
не влезает. Отбрасываем последнюю цифру из цепочки, она уйдёт в режим B.
`run % 2` как условие — идиома «нечётное»: любое ненулевое число истинно.

```python
    if use_c and run >= 2:
        if mode != "C":
            values.append(START_C if mode is None else CODE_C)
            mode = "C"
        for k in range(0, run, 2):
            values.append(int(text[i + k:i + k + 2]))
        i += run
        continue
```

`mode is None` — «мы ещё ничего не выдали, нужен START, а не CODE». `is` вместо `==`
для `None` — правильно: `None` синглтон, сравнение по идентичности и быстрее,
и не зависит от чужого `__eq__`.

`int(text[i+k:i+k+2])` — пара цифр как число: `"84"` → `84`. Значение символа
в режиме C **и есть** это число (0–99), поэтому конверсия прямая, без таблицы.
Красивое свойство стандарта.

`range(0, run, 2)` — третий аргумент это шаг. Идиома «идти парами».
Альтернатива, более «питоническая» для пар:

```python
chunk = text[i:i+run]
for a, b in zip(chunk[::2], chunk[1::2]):
    values.append(int(a + b))
```

`continue` в конце — вернуться к началу `while` с новым `i`, минуя ветку режима B.

```python
    if mode != "B":
        values.append(START_B if mode is None else CODE_B)
        mode = "B"
    ch = text[i]
    code = ord(ch)
    if code < 32 or code > 126:
        raise ValueError(f"символ {ch!r} нельзя закодировать в Code 128B")
    values.append(code - 32)
    i += 1
```

Режим B: значение символа = `ord(ch) - 32`. Пробел (32) → 0, `"A"` (65) → 33 и т.д.
Опять прямая арифметика вместо таблицы — так устроен стандарт.

**`f"{ch!r}"`** — конверсия `!r` в f-строке означает «применить `repr()` вместо `str()`».
Разница принципиальна в сообщениях об ошибках:

```python
ch = " "                    # неразрывный пробел
f"символ {ch} нельзя"            # "символ   нельзя"    — не видно, что не так
f"символ {ch!r} нельзя"          # "символ '\xa0' нельзя" — сразу понятно
```

Правило: **в диагностике всегда `!r`**. Три конверсии всего: `!r` (repr),
`!s` (str, по умолчанию), `!a` (ascii — экранирует не-ASCII).

Проверка `code < 32 or code > 126` отсекает кириллицу и управляющие символы.
Явное исключение вместо тихой подстановки — правильный выбор: `render.draw_barcode`
(строки 340–345) ловит его и рисует этикетку **без полос**, а фронтенд показывает
причину под полем ввода. Пользователь видит проблему, а не печатает нечитаемый код.

```python
if not values:
    values = [START_B]
```

Пустая строка: формально нужен хотя бы START, иначе `pattern()` упадёт на
`values[0]`. Результат — вырожденный, но валидный по структуре код.

#### Блок 4. Контрольная сумма и ширины — `pattern` (строки 68–84)

```python
values = encode(text)
start = values[0]
checksum = start
for pos, val in enumerate(values[1:], start=1):
    checksum += pos * val
values.append(checksum % 103)
values.append(STOP)
```

**Контрольная сумма Code 128** — взвешенная сумма по модулю 103:
`(старт + Σ позиция_i × значение_i) mod 103`, где позиции нумеруются с 1
сразу после стартового символа.

Почему 103: столько значений (0–102) может принимать символ данных.
Почему взвешенная, а не простая сумма: простая не различает **перестановку**
символов, взвешенная — различает. Классический приём, тот же в ISBN, IBAN, EAN-13.

**`enumerate(iterable, start=1)`** — второй аргумент задаёт начальное значение
счётчика. Без него пришлось бы писать `pos + 1` внутри цикла. `values[1:]` —
срез «всё кроме первого»; создаёт копию списка, что для 10–20 элементов неважно,
но на больших данных предпочтительнее `itertools.islice(values, 1, None)`.

Тонкость: **`values` мутируется после `encode`** — в него дописываются
контрольная сумма и STOP. `encode` вернул список, `pattern` его дополняет.
Работает потому, что `encode` каждый раз создаёт новый список, но связь неявная:
имя `encode` обещает «полное кодирование», а на деле возвращает полуфабрикат.
Докстринг это честно оговаривает («без стартового и контрольного» — хотя стартовый
как раз есть). Более честное имя — `_encode_data`.

```python
widths = []
for val in values:
    widths.extend(int(c) for c in _PATTERNS[val])
return {"widths": widths, "modules": sum(widths)}
```

**`list.extend(генератор)`** — добавить все элементы из итерируемого.
Отличие от `append`: `append` кладёт объект целиком (получился бы список списков).

`int(c) for c in "212222"` — **генераторное выражение** (не список!). Скобки не нужны,
когда это единственный аргумент функции. Разница со списковым включением:

```python
sum([x*x for x in range(10**6)])    # строит список на миллион элементов
sum(x*x for x in range(10**6))      # ничего не строит, идёт по одному
```

Здесь элементов 6 — разницы нет, но привычка полезная.

Возврат **словаря** вместо кортежа `(widths, modules)` — осознанный выбор:
результат уходит прямо в JSON (`server.py:164` → `return self.json(bc.pattern(code))`),
и на фронтенде читается как `data.modules`, а не `data[1]`. Формат функции
и формат API совпали, промежуточная конверсия не нужна.

## Concepts Explained

### Design Patterns Used

| Паттерн | Где | Зачем |
|---|---|---|
| Single source of truth | `pattern()` — единственный источник раскладки | Превью и печать не могут разойтись: это буквально один список чисел |
| Data as table, not code | `_PATTERNS` | Спецификация переносится один в один, ошибка локализуется в одной строке |
| Промежуточное представление | возврат ширин, а не картинки | Один кодек обслуживает PNG, TSPL и валидацию в UI |
| Fail loud on bad input | `raise ValueError` на некодируемый символ | Нечитаемый штрихкод хуже отсутствующего |
| Self-test entry point | `if __name__ == "__main__"` | Проверка модуля без тестового фреймворка |

### Key Technical Concepts

#### Концепт 1: Code 128 как кодировка с переключением режимов

**Что**: символьный набор, где смысл кода зависит от текущего режима, а переключение
между режимами — тоже символ. Классический **stateful encoding**.

**Почему здесь**: это стандарт, который стоит на настоящих этикетках CNH — сканеры
на складе уже настроены на него. Плюс режим C даёт вдвое более плотный код
для числовых артикулов, а на этикетке 72 мм шириной каждый модуль на счету.

**Когда применять (шире)**: stateful-кодирование встречается везде, где нужен
компромисс между размером алфавита и плотностью — UTF-8 (правда, там stateless),
Shift-JIS, escape-последовательности терминала, ISO 2022. Понимание «режим +
переключатель как символ» переносится напрямую.

**Trade-offs**:
* Плюсы: полный ASCII при высокой плотности для цифр; самопроверяемость (контрольная сумма); читается в обе стороны.
* Минусы: кодировщик должен решать задачу оптимизации (какой режим где выгоден); ошибка в выборе режима даёт валидный, но избыточно длинный код; отладка «на глаз» невозможна.

**Альтернативы**:
* **Code 39** — проще некуда (нет режимов, нет контрольной суммы), но ~30% длиннее и только заглавные+цифры.
* **EAN-13 / UPC** — фиксированная длина 13 цифр, для розницы; артикул CNH туда не влезет.
* **QR / DataMatrix** — двумерные, вмещают на порядки больше, но требуют 2D-сканера; линейные сканеры на складе их не прочтут.

**Что нужно знать, чтобы это понять**:
* Модуль как единица ширины — что штрихкод описывается не миллиметрами, а относительными единицами.
* Тихая зона (quiet zone) — белое поле по краям, без которого сканер не найдёт начало кода. Отсюда `BARCODE_ROW["width_frac"] = 0.70` в `layout.py:82`.
* ASCII-таблица — почему `ord(ch) - 32`.

#### Концепт 2: Контрольная сумма со взвешенными позициями

**Что**: `(Σ вес_i × значение_i) mod N`. Вес зависит от позиции, поэтому
перестановка двух символов меняет сумму.

**Почему здесь**: печать термотрансфером неидеальна — грязь на головке, замятие,
износ. Контрольная сумма превращает «сканер прочёл неверный номер» в «сканер
не прочёл ничего», а это разница между отгрузкой не той детали и повторным сканированием.

**Когда применять**: любой идентификатор, который человек или устройство может
прочесть с ошибкой — номер счёта, серийник, короткая ссылка.

**Trade-offs**:
* Плюсы: почти бесплатно (один символ), ловит одиночные ошибки и перестановки.
* Минусы: не исправляет, только обнаруживает; вероятность коллизии ≈ 1/103 при случайном шуме.

**Альтернативы**:
* **Простая сумма** — не ловит перестановки. Плохо, потому что перестановка соседних цифр — самая частая ошибка ручного ввода.
* **Luhn (mod 10)** — банковские карты; та же идея, другие веса.
* **Коды Рида — Соломона** — не просто обнаруживают, а **исправляют**; так работает QR, где до 30% кода можно потерять. Цена — существенная избыточность и сложность.

**Что нужно знать**:
* Модульная арифметика — почему `mod 103`, а не `mod 100`.
* Расстояние Хэмминга — формальная мера «сколько ошибок код различает».

#### Концепт 3: Промежуточное представление вместо готового артефакта

**Что**: функция возвращает не картинку, а описание (`{"widths": [...]}`),
из которого потребитель строит нужную ему форму.

**Почему здесь**: три потребителя с несовместимыми требованиями —
PNG в миллиметрах (`render.draw_barcode`), TSPL-битмап, и строка статуса в UI.
Если бы `pattern()` возвращала `Image`, второму и третьему пришлось бы её
переразбирать, а первому — пересэмплировать, теряя резкость краёв полос.

**Когда применять**: как только у результата больше одного потребителя,
или один из них хочет данные, а не пиксели. Это тот же принцип, что «парсер
отдаёт AST, а не отформатированный код» и «API отдаёт JSON, а не HTML».

**Trade-offs**:
* Плюсы: потребители независимы, тестировать легко (числа сравнивать проще картинок), точность не теряется на конверсиях.
* Минусы: каждому потребителю нужен свой код отрисовки (здесь — `draw_barcode` в `render.py` и `<rect>`-логика на фронте, если бы она была).

**Альтернативы**: вернуть SVG-строку (браузеру удобно, `Pillow` не умеет),
вернуть `Image` (готово к печати, но не масштабируется без потерь).

**Что нужно знать**: разница между растром и векторным описанием;
почему масштабирование растрового штрихкода — плохая идея (края полос размываются,
сканер теряет границы).

### Смежные концепции

- **Reed–Solomon и коды с исправлением ошибок** — следующий уровень после контрольной суммы; основа QR и DataMatrix.
- **Динамическое программирование для оптимального выбора режимов** — текущая эвристика (`run >= 4`) даёт хороший код, но не гарантированно кратчайший. Оптимум ищется DP по состояниям (позиция, режим) — классическая учебная задача.
- **GS1-128** — надстройка над Code 128 с идентификаторами применения (AI); если этикетки когда-нибудь пойдут в чужую логистику, понадобится именно она.
- **Печать штрихкодов и DPI** — почему ширина модуля должна быть кратна точке принтера, иначе округление «съедает» полосы. При 203 dpi модуль = 0.125 мм.

   или «переключить режим») и сравните с эвристикой на реальных номерах из каталога.

   * ручной правкой `_PATTERNS` — опечатка не упадёт, а даст нечитаемую этикетку;

   * масштабированием готовой картинки штрихкода — при 203 dpi один модуль это одна точка, любое дробное масштабирование ломает края полос.
