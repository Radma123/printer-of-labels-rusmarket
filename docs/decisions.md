# Технические решения

> Каждое решение — контекст → что решили → почему → альтернативы → последствия.
> Составлено по переписке с пользователем в предыдущей сессии Claude (Cowork).

## 1. Печать напрямую TSPL (raw), без BarTender/официального макета

**Контекст**: цель — программа, которая сама собирает этикетки из CSV-каталога
и отправляет на печать, без ручной работы в стороннем ПО.

**Решение**: скрипт формирует TSPL-команды сам и шлёт их принтеру байтами
через `lp -o raw`, минуя любой прикладной драйвер рендеринга.

**Почему**: BarTender/NiceLabel — это отдельный лицензируемый софт с своим
UI, интеграция с ним через файлы/COM/API избыточна для одной автоматической
задачи. TSPL — открытый и полностью описанный язык принтера (есть
официальный Programming Manual), задание получается 20-60 КБ и печатается
мгновенно.

**Альтернативы**: BarTender/NiceLabel (отклонено — лишняя зависимость и
интерфейс); печать через системный AirPrint-драйвер обычным
`NSPrintOperation`/`lp` без `-o raw` (отклонено — драйвер пытается
отрендерить страницу, а не передать байты как есть; для непонятных
принтеру данных выйдет мусор либо текст TSPL-команд на бумаге).

**Последствия**: скрипт жёстко привязан к CUPS-очереди типа raw и к
конкретному диалекту TSPL этого принтера. Если когда-нибудь поменяется
модель принтера на не-TSC — весь блок `build_job`/`bitmap_cmd` придётся
переписывать под её язык (ZPL/EPL/др.).

## 2. Кириллица — картинкой (BITMAP), а не встроенным шрифтом TSPL

**Контекст**: TSPL команда `TEXT` с встроенными шрифтами принтера кириллицу
не поддерживает (проверено на практике — печатает кракозябры).

**Решение**: весь текстовый блок этикетки рендерится в Pillow как
монохромное изображение и передаётся командой `BITMAP`; для штрихкода и
QR используются РОДНЫЕ команды принтера `BARCODE`/`QRCODE` (не картинка).

**Почему**: рисовать текст самому — единственный надёжный способ получить
кириллицу на этой модели без перешивки принтера кастомными шрифтами.
Штрихкод/QR оставлены нативными, потому что так они получаются чётче
(меньше риск нечитаемости сканером) и компактнее по объёму задания.

**Альтернативы**: закачать кастомный кириллический шрифт в память принтера
(`Bitmap Font Manager` в Diagnostic Tool) — отклонено как более хрупкое
и требующее лишнего шага настройки принтера; печатать латиницей/транслитом
— отклонено, пользователю нужен русский текст.

**Последствия**: доступность шрифта с кириллицей на машине, где запускается
скрипт, — это теперь **обязательное условие**. Отсюда список кандидатов
`FONT_CANDIDATES` и переменные `LABEL_FONT`/`LABEL_FONT_BOLD` для ручного
переопределения, если стандартные пути не найдутся.

## 3. Поиск в CSV — потоковое построчное чтение, без БД/индекса

**Контекст**: каталог CNH — 1.14 ГБ, 20 колонок, номера деталей не
отсортированы гарантированно.

**Решение**: `find_row()` читает файл построчно (`for raw in fh`) и
сравнивает начало строки с искомым номером, без загрузки в память, без
SQLite/pandas/индексации.

**Почему**: замеренный худший случай — 2.8 сек на полный проход. Для
разового ручного вызова «напечатать одну деталь» это приемлемо и не
требует ни этапа импорта в БД, ни поддержки этой БД в актуальном
состоянии при обновлении CSV.

**Альтернативы рассматривались, но не реализованы**: импорт в SQLite с
индексом по part_number (было бы быстрее при частых повторных запросах,
но добавляет шаг синхронизации при каждом обновлении CSV-файла от
поставщика — сочтено лишней сложностью для текущего объёма использования);
`pandas.read_csv` с чанками (не нужен, plain-python built-in `csv` модуль
достаточен и быстрее по памяти для точечного поиска одной строки).

**Последствия / ограничение**: если понадобится печатать пачками (десятки
деталей за раз), стоит рассмотреть один проход по файлу с построением
словаря нужных номеров сразу, а не вызывать `find_row` в цикле (иначе
N деталей × O(файл) = медленно при больших N). Сейчас этот сценарий
в CLI не реализован (`--copies` — это N копий ОДНОЙ детали, не батч
разных номеров).

## 4. Калибровка принтера: числа выставлены вручную в Diagnostic Tool + физическая калибровка кнопкой

**Контекст**: комплект — этикетки 100×72 мм (высечка/GAP), риббон Wax 104 мм.
Автокалибровка через диалог "Calibrate Sensor" → Auto Calibration в
диагностической утилите TSC (Windows) не заполнила поля Paper Height/Gap
автоматически (известная особенность этой версии утилиты — лента при этом
физически моталась, то есть замер шёл, но обратно в UI не отобразился).

**Решение**: значения выставлены вручную во вкладке Printer Configuration →
Common: `Paper Width=100mm`, `Paper Height=72mm`, `Media Sensor=GAP`,
`Gap=3mm` (уточнено линейкой по факту, не взято из документации по
умолчанию — паспортное минимальное значение было 2 мм, реальное на этом
рулоне оказалось 3 мм), `Gap Offset=0`, `Speed=4`, `Density=8`,
`Ribbon=ON`, `Direction=1,0`, `Reference=0,0` → кнопка **Set**, подтверждено
обратным **Get** (принтер вернул те же значения — TE200 Version A2.16 EZD,
serial TEAT25390669).

**Почему**: `Set`/`Get` показали, что значения реально сохранились в
энергонезависимой памяти принтера — то есть настройка не привязана к
Windows-ВМ и переживёт переключение принтера на macOS.

**Альтернативы**: полагаться только на автокалибровку через диалог —
отклонено, потому что в первый раз она не сработала видимо (поля
остались пустыми); калибровка только кнопкой на корпусе при включении
питания — тоже делалась (см. ниже), но менее точная, чем явное указание
размера через ПО.

**Последствия — НЕЛЬЗЯ случайно отменить**:
- Кнопка «Factory Default» / «Reset Printer» в Diagnostic Tool сотрёт
  все эти настройки до заводских (4×4 дюйма, GAP 3.0 мм по умолчанию
  прошивки, датчик высечки) — после этого калибровку нужно будет повторять
  полностью заново (руками или через Auto Calibration).
- Значения `LABEL_W_MM/LABEL_H_MM/GAP_MM/SPEED/DENSITY` в `tsc_label.py`
  **продублированы** и должны совпадать с тем, что реально прошито в
  принтере. Если кто-то перекалибрует принтер на другой размер этикеток
  физически (другой рулон) — обязательно обновить эти константы в скрипте,
  иначе получится рассинхрон и брак печати (как было с обрезанной рамкой
  на раннем тесте, см. `docs/current-state.md` → «Известные проблемы»).

## 5. Первый тест печати шёл через Windows-ВМ и Diagnostic Tool, финальная работа — только через macOS напрямую

**Контекст**: у пользователя есть Windows-ВМ (Parallels) с фирменной
утилитой TSC. USB-принтер можно пробросить только в один гостевой ОС
одновременно — либо в ВМ, либо видит хост-Mac.

**Решение**: калибровка сделана один раз в Windows-ВМ (там есть только
подходящий тулинг — Diagnostic Tool под Windows), после чего USB
отсоединён от ВМ и принтер добавлен напрямую в macOS для повседневной
работы. Windows-ВМ для обычной эксплуатации больше не нужна.

**Почему**: калибровочные настройки хранятся в энергонезависимой памяти
самого принтера (см. решение №4), а не в драйвере хоста — поэтому
переключение USB между гостем и хостом их не сбрасывает.

**Последствия**: если принтер физически переключат обратно в ВМ (например,
для повторной калибровки другого рулона) — на macOS в этот момент очередь
`TSC_TE200` перестанет отвечать (устройство `usb://TSC/TE200?...` пропадёт
из системы). Это ожидаемо, не баг.

## 6. Форсирование `LC_ALL=C`/`LANG=C` для вызовов `lpstat`/`lp` из Python

**Контекст**: macOS пользователя настроена на русский язык интерфейса.
`lpstat -p` возвращает локализованный вывод («принтер X свободен»), а
парсер в `queues()` искал английский префикс `"printer "` — из-за этого
скрипт был уверен, что очередей нет, хотя `TSC_TE200` реально существовала
и работала (пользователь печатал через TextEdit).

**Решение**: все вызовы `lpstat`/`lp` из скрипта теперь идут с
`env=dict(os.environ, LC_ALL="C", LANG="C")` (константа `_CUPS_ENV` в
`tsc_label.py`) — только для этого дочернего процесса, на остальную
систему/локаль пользователя не влияет.

**Почему**: это единственный способ получить предсказуемый (английский,
задокументированный) формат вывода CUPS-утилит независимо от локали
конкретной машины, не заставляя пользователя менять системный язык.

**Альтернативы**: парсить `lpstat` по позиции слова / регуляркой, не
завязываясь на конкретный язык (отклонено — хрупко, слов «свободен»/
«idle»/«free» и т.п. по разным локалям заранее не предугадать); просить
пользователя сменить язык системы (отклонено — избыточное вмешательство
ради одного скрипта).

**Последствия**: если в проект добавят другие вызовы CUPS-утилит из
Python — их тоже нужно оборачивать `env=_CUPS_ENV`, иначе баг повторится
в новом месте.
