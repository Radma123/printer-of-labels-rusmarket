## Главная цель задачи

Пользователь — автосервис/склад запчастей (каталог CNH — детали
сельхозтехники Case IH и аналоги). Нужна программа: по каталожному номеру
детали из CSV (1.14 ГБ, 20 колонок) сформировать и напечатать этикетку
100×72 мм на принтере TSC TE200 (штрихкод + наименование RU/EN + метаданные),
без стороннего софта для печати этикеток (BarTender и т.п.), напрямую из
Python.

## Что полностью реализовано и подтверждено работающим

1. **Принтер физически настроен и откалиброван.** Через TSC Diagnostic
   Tool (Windows-ВМ, Parallels) выставлены и подтверждены обратным Get:
   Paper Width 100 мм, Paper Height 72 мм, Media Sensor = GAP, Gap 3 мм,
   Speed 4, Density 8, Ribbon ON, Direction 1,0, Reference 0,0. Печать
   тестовой страницы (Print Test Page) даёт ровно одну этикетку высотой
   ровно 72 мм — калибровка зазора работает корректно.
2. **Принтер подключён к macOS** как CUPS-очередь `TSC_TE200`
   (`usb://TSC/TE200?serial=000001`), драйвер MAC-1.29 установлен.
   Подтверждено: `lpstat -a` видит очередь, она принимает задания.
   Обычная печать (текст из TextEdit) физически работает — риббон,
   лента, головка исправны.
3. **Скрипт `tsc_label.py` написан и синтаксически проверен** (`python3
   -m py_compile` проходит без ошибок). Умеет:
   - `--check` — диагностика окружения (Pillow, шрифт, CUPS-очереди, CSV);
   - `--pn НОМЕР` — найти деталь в CSV и подготовить этикетку;
   - `--find ПОДСТРОКА` — подсказать похожие номера;
   - `--demo` — тестовая этикетка без CSV;
   - `--preview PNG` — сохранить превью картинкой, не печатая;
   - `--out FILE` — сохранить готовое TSPL-задание в файл;
   - `--printer QUEUE` — отправить на печать через `lp -o raw`;
   - `--usb` — печать напрямую в USB через pyusb (код есть, **не
     протестирован ни разу**, pyusb на Mac пользователя не подтверждён
     установленным — не приоритет, т.к. CUPS raw уже работает);
   - `--copies N`.
4. **Поиск в CSV работает и проверен на реальных данных**: детали
   `C5NNF892A` (ЖЕСТКАЯ ТРУБКА) и `1-32-574-086` (ШТИФТ,35mm OD x 114mm L)
   успешно находятся, превью отрисовывается корректно (кириллица читаема,
   текст не обрезан, штрихкод/QR-зоны на месте). Полный проход по файлу
   (номер в последней строке, `V47456`) — 2.8 сек, приемлемо.
5. **Исправлен баг локали** (см. `docs/decisions.md` п.6): `lpstat -p`
   на русской macOS выводит «принтер X свободен», а не «printer X is
   idle» — парсер в `queues()`/`send_cups()` этого не учитывал и не
   находил уже реально существующую очередь `TSC_TE200`. Исправлено
   форсированием `LC_ALL=C, LANG=C` для дочерних процессов `lpstat`/`lp`.
   Патч внесён в файл на диске, синтаксис проверен.

## Что подтверждено ПОСЛЕ патча локали (обновление)

Пользователь подтвердил текстом «всё печатается идеально» после патча
`_CUPS_ENV` (п.5 в `docs/decisions.md`). Это значит:
- `python3 tsc_label.py --check` теперь видит очередь `TSC_TE200`;
- `--demo --printer TSC_TE200` и/или печать реальных деталей из CSV
  проходит через raw-режим корректно — этикетка ложится ровно, без
  обрезаний и сдвигов.

**Важная оговорка**: пользователь подтвердил результат одной фразой, без
фото и без указания, какая именно команда запускалась (`--demo` и/или
конкретный `--pn`). Явно проверенным строкой из чата можно считать только
факт «печать работает и выглядит хорошо» — если нужно, для очистки
совести можно попросить у пользователя фото этикетки с реальными данными
(`--pn`) для протокола, но блокером это не является.

Базовый путь **CSV → превью → TSPL → CUPS → физическая этикетка**
считается рабочим и закрытым.

Базовая печать одной детали по номеру подтверждена рабочей. Следующий

## Следующие шаги после этого (не начаты, но обсуждались как цель)

- Пользователь хочет **автоматическую программу**, которая сама будет
  «составлять этикетки и отправлять их на печать» — то есть текущий CLI
  с одним `--pn` за вызов, скорее всего, промежуточный этап, а не
  конечная цель. Не обсуждалось явно: нужен ли пакетный режим (список
  номеров → пачка этикеток за один запуск), нужен ли скан штрихкода как
  ввод, нужен ли GUI/веб-интерфейс, нужна ли интеграция с 1С/складской
  системой. **Это нужно уточнить у пользователя**, а не додумывать.
- `--usb` путь (печать мимо CUPS напрямую в USB) написан, но не
  протестирован и, возможно, не нужен вовсе, раз CUPS raw работает —
  не тратить время на него без явного запроса.
- В папке проекта остался мусор от тестовых прогонов текущей сессии:
  `_test_output/`, `__pycache__/`, `preview.png`, `rich_preview.png` в

  автоматических прав на удаление файлов с диска пользователя в рамках
  предыдущей сессии (можно предложить пользователю удалить руками или
  запросить у него разрешение).
- Нет `requirements.txt` — стоит завести (`Pillow`), если проект будет
  жить дальше и переноситься на другие машины.

## Известные проблемы / что уже пробовали и почему не сработало

- **Auto Calibration в Diagnostic Tool (Windows) не заполнила поля
  Paper Height/Gap автоматически** при первой попытке, хотя лента
  физически моталась (сенсор что-то мерил). Причина не выяснена до
  конца — списано на особенность конкретной версии утилиты (1.63).
  **Обошли** — выставили размеры вручную во вкладке Printer Configuration
  и подтвердили через Get. Если у следующего агента/пользователя это
  повторится на новом рулоне — сразу переходить к ручному вводу, не
  тратить время на повторные попытки Auto Calibration.
- **Обрезанная рамка на самом первом тесте** (Print Test Page из
  Diagnostic Tool, ДО перехода на macOS): верхняя и левая линии рамки
  тестового узора не пропечатались на этикетке — оказались на соседней.
  Объяснено нормальным аппаратным допуском между датчиком зазора и
  печатающей головкой (несколько мм) и подтверждено физическим осмотром
  подложки/зазора пользователем. **Не является багом скрипта** — сам
  `tsc_label.py` печатает с отступом `MARGIN_MM=3.0` мм от края именно
  чтобы этот эффект не задевал реальный контент. Если на новых тестах
  снова появится обрезание уже РЕАЛЬНОГО содержимого (не тестовой рамки
  принтера) — это уже другая история, разбираться заново.
- **`python3` без Pillow** — на самом первом заходе пользователь получил
  «программа не работает» без деталей. Причина не была надёжно
  диагностирована (не удалось получить точный traceback от пользователя),
  скрипт был превентивно переписан с graceful-деградацией (`--check`
  показывает, стоит ли Pillow, вместо необработанного `ImportError` при
  импорте) и с более широким списком путей к шрифтам (в старой версии
  запасные пути были Linux-специфичными и не существовали бы на Mac,
  что тоже могло валить скрипт с непонятной ошибкой при отсутствии
  Arial). Оба риска устранены в текущей версии файла, но исходная
  причина падения «не работает» у пользователя документально не
  подтверждена (не было точного текста ошибки).

## Ограничения, о которых нужно помнить

- `find_row()` берёт **первое** совпадение по номеру и останавливается —
  если в каталоге есть дубликаты part_number с разными данными, вернётся
  только первая строка. Уникальность номеров по всему файлу не
  проверялась.
- CSV читается построчным `for raw in fh` — если у какой-то строки
  реально больше/меньше полей, чем в заголовке (битая строка, перенос
  внутри кавычек на несколько физических строк и т.п.), `dict(zip(hdr,
  row))` в `find_row` молча обрежет по короткому списку — данные могут
  съехать по колонкам без явной ошибки. Не проверялось на всём файле,
  только на 2 примерах.
- Печать «пачкой разных деталей» в CLI не реализована — `--copies`
  печатает N копий ОДНОЙ и той же детали.
- `--usb` — код есть, но не проверялся; если понадобится, сначала
  `pip install pyusb` + `brew install libusb`, затем тестировать отдельно.

## Новое: веб-приложение label_app/ (31.08.2026)

По запросу пользователя рядом с CLI-скриптом `tsc_label.py` (он не
тронут и продолжает работать) сделано отдельное веб-приложение —
`label_app/`. Design MCP (claude.ai/design) для импорта макета
`Label 100x72.dc.html` был недоступен в сессии (нет авторизации
`/design-login`, non-interactive), поэтому этикетка собрана заново
по трём фото реальных этикеток CNH, которые прислал пользователь
(`PXL_20260818_*.jpg` в корне проекта) — совпадение по расположению
блоков, а не сверено с самим макетом Claude Design.

Запуск:
```
python3 label_app/server.py     # http://127.0.0.1:8765, слушает только localhost
```

Что внутри (`label_app/`):
- `server.py` — стандартная библиотека Python, без внешних зависимостей
  веб-фреймворка; отдаёт статику и небольшой JSON API (`/api/*`).
- `catalog.py` — поиск по CSV (1.14 ГБ) через отдельный отсортированный
  индекс `<csv>.pnidx` (строится кнопкой в интерфейсе, ~2 мин один раз)
  и бинарный поиск по mmap — миллисекунды на запрос вместо полного
  перебора файла.
- `translate.py` — перевод EN→IT/FR/DE/ES/PT через бесплатный публичный
  API MyMemory (`api.mymemory.translated.net`, без ключа, лимит 5000
  симв/сутки анонимно). Результаты кэшируются в
  `label_app/translation_cache.json`, поэтому один и тот же текст не
  тратит лимит повторно и работает офлайн после первого перевода.
  **Важно:** это не готовый словарь — при исчерпании лимита или
  недоступности сети поля перевода останутся пустыми/с ошибкой, это
  штатное поведение (см. `errors` в ответе API), не баг.
- `barcode.py` — Code128 (та же кодировка, что на оригинальных этикетках
  CNH) в виде списка ширин полос; используется и превью в браузере
  (SVG), и рендер PNG/TSPL — расхождений между ними быть не может.
- `layout.py` — единственный источник координат этикетки в мм; фронтенд
  получает его через `/api/layout` и строит DOM-превью по тем же
  цифрам, что использует серверный рендер (`render.py`) для точного
  PNG-превью и печати.
- `static/` — фронтенд (`index.html` + `app.js` + `style.css`), без
  сборки, без npm.

Проверено вручную в этой сессии (см. переписку) через Browser-инструмент:
- поиск по каталожному номеру (индекс/mmap) — работает, ~секунда с учётом
  сети на перевод;
- перевод на 5 языков через MyMemory — работает, результаты близки к
  реальным этикеткам CNH (сверено на `FUEL FILTER`/`OIL FILTER`);
- превью в браузере (DOM, миллиметры) и точное превью (`/api/preview.png`,
  203 dpi через Pillow) визуально совпадают;
- `lpstat -p`/`-a` на этой машине выводят статус **на русском даже с
  `LC_ALL=C`** (macOS берёт локаль системно, не из env процесса) — старое
  предположение в `tsc_label.py` о том, что `LC_ALL=C` форсирует
  английский вывод, **не подтвердилось на практике**. `server.py`
  использует `lpstat -e` (список имён очередей без переводимого текста)
  вместо парсинга `lpstat -p` — это работает независимо от локали.
  Если `tsc_label.py` будет дальше дорабатываться, стоит перенести туда
  такое же исправление.
- физическая печать на TSC_TE200 из этого приложения **не выполнялась**
  в рамках сессии (это необратимое действие с реальным принтером,
  оставлено на подтверждение пользователя) — `/api/print` и сборка TSPL
  (`render.build_tspl`) проверены только на корректность байтов задания,
  не на реальном принтере.

## Обновление: реализован реальный макет из Claude Design (31.08.2026, позже в тот же день)

Пользователь прислал handoff-архив из Claude Design
(`~/Downloads/Этикетка для масляного фильтра-handoff.zip`) с настоящим
файлом `Label 100x72.dc.html` и тремя реальными логотипами (CNH Genuine
Parts, значок «глаз», сертификат FSC — лежат в
`untitled/project/logos/*.png` в архиве, а также продублированы
пользователем в `labels_png/1.png,2.png,3.png` в корне проекта). Старая
версия `label_app/`, описанная в предыдущей записи этого файла (с
нарисованными от руки логотипами, строкой брендов внизу и RU-строкой),
**заменена** на точную реализацию этого макета.

**Важное открытие: макет портретный (72мм×100мм), а не альбомный.**
`<doc-page width="72mm" height="100mm">` в исходнике — то есть 72мм
ширина, 100мм высота, как и на всех присланных фото реальных этикеток
CNH (они явно вытянуты по вертикали). Число в имени файла
(«100x72») не совпадает с фактической ориентацией контента внутри —
скорее всего просто осталось от раннего черновика в Claude Design.

Физический принтер откалиброван на рулон 100мм (поперёк головки) ×
72мм (вдоль подачи) — те же два числа, просто переставленные. Поэтому
`render.build_tspl()` рисует этикетку в родной ориентации макета
(72×100), а перед отправкой на печать **поворачивает готовую картинку
на 90°** — так она укладывается на рулон без обрезки и без искажения
пропорций (72↔72, 100↔100 совпадает ровно). **Направление поворота
(по часовой/против) не проверено на реальном принтере** — в интерфейсе
есть чекбокс «перевернуть на 180° при печати» на случай, если первая
физическая этикетка ляжет текстом не в ту сторону. Это единственная
физическая неопределённость, которая осталась в этой сессии: всё
остальное проверено через `/api/preview.png` (серверный PNG-рендер,
203 dpi) и визуально в браузере, но реальная печать не выполнялась.

Что изменилось в коде:
- `label_app/layout.py` — переписан с нуля, координаты 1:1 из
  inline-style `Label 100x72.dc.html` (шапка с тремя логотипами через
  space-between, 6 строк наименования, «Made in», ряд штрихкода 73px/32px,
  номер детали моноширинным шрифтом по центру, PCS прижат к низу через
  эквивалент `margin-top:auto`). Никакой RU-строки, никакой строки
  брендов внизу, никакого доп. кода (partCode/BNZ50) — этого нет в
  макете, при первой реализации (см. запись выше) это было добавлено
  по фото, не по факту макета.
- `label_app/render.py` — рисует по этой геометрии; логотипы вставляются
  реальными PNG через тот же приём crop-через-offset, что в macете
  (контейнер + увеличенная картинка со сдвигом), а не рисуются вручную.
  Обнаружена и обойдена реальная теснота по вертикали: при полных 6
  строках наименования расчётная высота контента (по CSS-константам
  макета) вплотную подходит к нижнему краю 100мм — с шрифтом Arial в
  Pillow (метрики чуть шире эталонного Helvetica в браузере) строка PCS
  раньше вылезала за край. Исправлено мягким ограничением сверху в
  `draw_pcs()` (см. комментарий в коде) — строка PCS теперь всегда
  видна целиком, ценой небольшого сокращения отступа перед ней именно
  в этом самом плотном случае.
- `label_app/static/index.html`/`style.css` — разметка превью теперь
  дословно копирует структуру и inline-стили макета (тот же flexbox,
  те же mm/px), поэтому браузер сам считает раскладку — расхождений с
  макетом по построению почти нет (кроме автосжатия шрифта для строк
  наименования и номера детали при слишком длинном переводе — в
  макете такого нет, это подстраховка для реальных длинных наименований
  из CSV, которых не было в примере макета).
- `label_app/static/logos/logo1.png,logo2.png,logo3.png` — теперь
  настоящие файлы из макета (были скопированы также в `labels_png/` в
  корне проекта самим пользователем под другими именами — тот же набор
  из трёх файлов, 1:1 совпадают по размеру в байтах).
- Убраны поля «доп. код справа» (BNZ50), «код FSC» (текст поверх — он
  и так внутри PNG логотипа FSC) и «строка брендов внизу» — их нет в
  макете. Штрихкод остаётся настоящим Code 128 (barcode.py), а не
  декоративным узором из прототипа `.dc.html` (там штрихкод рисуется
  случайным псевдо-узором чёрных/белых полос одинаковой ширины — не
  сканируется; реальный Code 128 нужен для склада, поэтому сохранён
  из предыдущей версии).
